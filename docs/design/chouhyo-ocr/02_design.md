## 3. 構成

### 3.1 2層構成と責務境界

```
┌─────────────────────────────────────┐
│ Tauri デスクトップアプリ（GUI）      │
│  ・実行画面        ・テンプレート編集画面 │
│  → 処理ロジックを持たない            │
└──────────────┬──────────────────────┘
               │ sidecar 起動＋stdout の JSON Lines
┌──────────────▼──────────────────────┐
│ Python コア（CLI）                   │
│  run / remap / render / status /     │
│  verify / purge                      │
└──┬────────┬────────┬────────┬───────┘
   │        │        │        │
 Poppler  Vision   SQLite   出力
```

GUI が持つのはファイル選択・コアの起動・進捗の表示・JSON の読み書きだけ。**OCR・位置合わせ・丸印判定・出力生成を GUI 側で実行しない**（要件 §5.10）。CLI 単体で全機能を実行できる状態を維持する（要件 §3.5）。

### 3.2 CLI サブコマンド

| コマンド | 役割 | API 送信 |
|---|---|---|
| `run` | 入力フォルダを一括処理し中間データと出力を生成する | する |
| `remap` | 既存トークンからセルを作り直す（**テンプレート変更後**） | しない |
| `render` | 既存セルから .xlsx / .csv を作り直す（**閾値変更後**） | しない |
| `detect-grid` | 画像から**枠候補**を返す（§6.9）。テンプレート編集画面が呼ぶ | しない |
| `status` | 進捗と各ページの状態を表示する | しない |
| `verify` | 資格情報の読取可否と Poppler の実行可否を確認する | しない |
| `purge --yes` | 中間データを削除する。`--yes` なしでは実行しない | しない |

`detect-grid` をコア側のサブコマンドにするのは、要件 §5.10「編集画面は処理ロジックを持たず Python コアの呼び出しに徹する」を守るため。副次的な利点として、**枠候補の生成が GUI なしで検証できる**——M6（Day4 夜〜Day5）を待たずに CLI で作り込める。

`remap` と `render` を分けるのは、**〓判定を cell へ焼き込まない**ため。cell には読取値と信頼度だけを持ち、〓判定は `render` 時に閾値を当てて行う。こうすると要件 §5.8「閾値変更後、API へ再送信することなく再出力できる」が `render` 単独で成立し、テンプレートを変えたときだけ `remap` へ戻る。

### 3.3 `run` の処理フロー（1ページ分）

```
F1 列挙        対象拡張子のファイルを走査
F2 展開        PDF → PNG（pdftoppm）／画像はそのまま     → page 行 INSERT
F3 切り出し    faces[].source の矩形で面を切り出す（v1 は上下2面）
F4 位置合わせ  面ごとに独立して傾き・スケールを補正       → alignment 行
F5 再結合      補正後の2面を縦に戻して1枚にする
F6 送信        Vision へ1リクエスト（1画像＝1リトライ単位） → token 行
F7 割付        トークンをテンプレート矩形へ割り当てる      → cell 行
F8 丸印        選択式セルの環状帯スコアを測る             → era_score 行
F9 出力        cell から .xlsx と .csv を生成
```

**不変条件**: `page` 行が存在するなら、対応する展開画像の書き込みは完了している。F2 は画像を書き終えてから `page` 行を INSERT する（実装レビュー S6）。この順序が崩れると F4 が存在しない画像を読みに行く。

F5（再結合）を置く理由は課金。要件 §5.3 が「1リクエスト＝1画像。複数画像を束ねない」と定めており、面ごとに2回送ると1帳票あたりの送信が2倍になる。位置合わせは面ごとに独立して行い、送信は1枚に戻してから1回だけ行う。トークン座標は再結合後の座標系で返るため、面の原点オフセットを引いて面ローカルへ戻す。

## 4. データ構造 ★本番として確定

### 4.1 項目ID（field_id）体系

テンプレート・220列・中間データの3者を繋ぐ唯一のキー。

| 種別 | 形式 | 例 |
|---|---|---|
| 単発欄 | `<グループ名>_<項目名>` | `person_氏名` `person_生年月日_元号` |
| 繰り返し欄 | `<table_id>_<2桁連番>_<列名>` | `family_01_続柄` `detail_01_来店年月日_年` |

繰り返し欄の形式は要件 §5.6 の記載どおり。単発欄の `person_` 接頭辞は要件に明示がない ※解釈。

**`field_id` は面（`face_id`）と独立**にする。`person_` は「本人欄というグループ」を指すのであって「表面」を指すのではない。面は画像を切り出す単位、`field_id` は出力列を指す名前で、対応づけを固定すると様式が変わったとき（同じ項目が別の面へ移る、面が増える）に列名まで動く。

**連番の割り当て**: ブロックを定義順に走り、行を跨いで通し番号を振る。家族欄は左ブロックが `01`〜`05`、右ブロックが `06`〜`10`。明細は左が `01`〜`14`、右が `15`〜`28`。読み順「左→右」は要件 §3.1 で ※解釈 と明示されているものをそのまま採る。

**この生成規則はコアとテンプレート編集画面で共有する。** 要件 §8-14 が「エディタが書き出した JSON をコアがそのまま読めること——エディタ専用の読み込み経路・変換工程をコア側に作らない」を要求しているため、ID を生成するのは片側だけにし、もう一方は同じ規則を実装して一致を検証する。

### 4.2 テンプレートスキーマ

矩形の列挙ではなく**テーブル定義**にする。要件 §5.2 が「欄座標・表裏分割位置・除外領域・家族欄と明細の**行数**はテンプレートに定義」としており、行数が属性である以上、行を1つずつ列挙する前提ではない。矩形を並べると欄は概算140個になるが、テーブル定義なら手で決める数値は20〜30個規模に収まる。

```json
{
  "schema_version": 1,
  "template_id": "chouhyo-v1",
  "render_dpi": 300,
  "image": { "width": 2480, "height": 3508 },
  "record": { "pages": 1 },
  "faces": [
    {
      "face_id": "front",
      "source": { "page_offset": 0, "rect": { "x": 0, "y": 0, "w": 2480, "h": 1754 } },
      "exclusions": [
        { "id": "ring_left", "rect": { "x": 0, "y": 0, "w": 80, "h": 1754 } }
      ],
      "fields": [
        { "field_id": "person_氏名", "kind": "text",
          "rect": { "x": 420, "y": 180, "w": 760, "h": 90 } },
        { "field_id": "person_生年月日_元号", "kind": "choice",
          "rect": { "x": 420, "y": 300, "w": 150, "h": 70 },
          "choice_marks": [
            { "value": "昭", "rect": { "x": 424, "y": 304, "w": 42, "h": 62 } },
            { "value": "平", "rect": { "x": 470, "y": 304, "w": 42, "h": 62 } }
          ] }
      ],
      "tables": [
        {
          "table_id": "family",
          "row_pitch": 62,
          "row_height": 56,
          "blocks": [
            { "origin": { "x": 120, "y": 820 }, "rows": 5 },
            { "origin": { "x": 1280, "y": 820 }, "rows": 5 }
          ],
          "columns": [
            { "name": "続柄",         "x_offset": 0,   "width": 120, "kind": "text" },
            { "name": "生年月日_元号", "x_offset": 420, "width": 90,  "kind": "choice",
              "choice_marks": [ { "value": "昭", "x_offset": 424, "width": 26 },
                                { "value": "平", "x_offset": 452, "width": 26 } ] }
          ]
        }
      ]
    },
    { "face_id": "back",
      "source": { "page_offset": 0, "rect": { "x": 0, "y": 1754, "w": 2480, "h": 1754 } } }
  ]
}
```

**この例示は形を見せるためのもので、要素を間引いてある**（除外領域は3つ・家族欄の列は6つ・選択肢は3つが実際の数）。完全な制約は `schema/template.schema.json` にある。

**座標系は2つある。**

| 空間 | 原点 | 寸法 | この空間で書く矩形 |
|---|---|---|---|
| 入力ページ座標 | 展開画像の左上 | `image.width` × `image.height` | `faces[].source.rect` のみ |
| 面ローカル座標 | 位置合わせ後の面画像の左上 | **その面の `source.rect` の `w` × `h`** | `exclusions`・`fields[].rect`・`tables[]` |

`image` は**入力ページ1枚の期待サイズ**であって面のサイズではない。展開画像をまずこの寸法へ正規化し、`source.rect` で切り出し、**位置合わせの前後で面の寸法（`rect.w` × `rect.h`）を変えない。** 面ローカル空間の大きさが `source.rect` から一意に決まるので、テンプレートに面サイズを書く欄は設けない。

面を独立に補正するため、欄の座標をページ全体の座標では持てない。

**`record` と `faces[].source` を分けている理由**

ここは汎用化したときに真っ先に割れる箇所なので、v1 から分けて持つ。潰れやすい2つの概念とは:

| 概念 | 持ち方 | 何が変わるか |
|---|---|---|
| **ページ → 面の切り出し** | `faces[].source`（どのページのどの矩形か） | 上下2分割／左右2分割／4分割／分割なし |
| **面 → 帳票（出力1行）の集約** | `record.pages`（1帳票が消費する入力ページ数） | 1ページ1帳票／2ページ1帳票（両面スキャン） |

「表裏分割位置」を1本の線として持つと、この2つが同時に固定される。線1本では左右分割も4分割も表現できず、そもそも**別ページに裏面がある様式**（両面スキャンの素直な出力）を表現する場所がない。`source` に `page_offset` を持たせておけば、面がページを跨いでも同じ構造で書ける。

出力行数の関係式も `record.pages` で一般化される。要件 §3.4 の「入力ページ数＝出力行数」は `pages = 1` の場合であり、一般には:

```
出力行数 = 入力ページ数 ÷ record.pages   （割り切れなければ実行前にエラーで停止）
```

**v1 の実装は範囲を絞る。** `record.pages` は `1`、`source.page_offset` は `0`、`face_id` は `front` / `back` のみを受け付け、**それ以外はテンプレート読み込み時に拒否する**（`schema_version` と同じく黙って続行しない）。スキーマは将来を表現できるが実装は v1 の範囲に閉じる、という線引きにする。汎用化のときに直すのは受け入れ範囲の判定と面の反復であって、テンプレートの書式ではない。

**エディタ側は変わらない。** 要件 §5.10 ⑤「表裏分割位置の指定」は水平線1本のドラッグのままでよく、保存時に2つの `source.rect` へ展開する。UI の単純さと、スキーマの表現力を別々に持てる。

**展開規則**: `blocks` を定義順に走り、各ブロックで `rows` 回だけ `origin.y + row_pitch * i` を計算して行の上端を求める。列は `origin.x + x_offset` と `width`、高さは `row_height`。行の通し番号はブロックを跨いで連番。

**`subfields`（複合セル）**: 家族欄の生年月日は物理的に1セルで、「7.7.20」とまとめ書きされる（実測）。テンプレートでは `subfields: ["年","月","日"]` を持つ1列とし、**1矩形の読取値を機械分割して3出力列へ展開する**（分割規則は D-23）。明細の年月日は物理3サブセルなので使わない——**subfields は物理と出力の粒度が違うときだけの装置**。

**テーブル内 `choice_marks` の縦位置**: 家族欄の昭平令は行内へ小さく縦積み印字される（実測・各マーク高さ約33px）。`y_offset`/`height` で行内の縦位置を指定する。省略時は行全体。

**`kind`** は `text`（文字ベース）と `choice`（選択式）の2値のみ。要件 §5.2「抽出方式は項目種別で決まり、項目名の命名規則には依存しない」を、この属性1つで担保する。元号は `choice` の一例であって特例ではない。

**`render_dpi`** をテンプレートに持たせるのは ※解釈。設定ファイルの6項目（要件 §5.8）に dpi は含まれないが、座標は dpi に依存するため、座標と同じファイルに置かないと不整合が起きる。PDF 展開はこの値で行う。

**この構造の正本は `template.schema.json`。** 上の JSON は読むための例示であって、実装が従うのはスキーマファイルの方。両者が食い違ったらスキーマを正とし、本節の例示を直す。

スキーマを別ファイルに切り出すのは言語をまたぐため。要件 §8-14 が「エディタが書き出した JSON をコアがそのまま読めること——エディタ専用の読み込み経路・変換工程をコア側に作らない」を要求しており、Python コアと TypeScript エディタが構造を別々に解釈すれば、ここが最初にズレる。コアは読み込み時に、エディタは保存前に、同じファイルで検証する。検証の実装は両側に置くが、**正本は1ファイル**とする。

**`schema_version` の扱い**: 既知のバージョンでなければ**読み込みを拒否する**。自動マイグレーションも「たぶん読める」フォールバックも実装しない。v1 は `1` のみを受け付ける。座標定義を取り違えたまま処理を続けると、全ページが誤った列へ入った成果物になり、要件 §8 第1層（1件でも不合格）に直撃する。読めないなら止まる方が安い。

### 4.3 列定義（テンプレートから導出する）

**列リストをコードへ持たない。テンプレートから導出する。** 抽出対象列に必要な情報——どの欄があるか、テーブルが何行あるか、各行が何列か——はすべてテンプレートに入っている。列リストを別に持つと同じ情報が2箇所になり、テンプレートで行数を5→6に変えても列が追従しない。様式が増えたときに「様式ごとに列リストをコードへ足す」ことになり、要件 §9 が「テンプレートへ外出ししてあるから様式を追加できる」と言っている前提を壊す。

**導出規則**

```
列 = 管理6列
   + 各 face（faces の定義順）について
       fields[] の定義順に1列ずつ                      → field_id
       tables[] の定義順に、blocks を跨いだ行連番 × columns[] の定義順
                                                       → <table_id>_<2桁連番>_<name>
```

**テンプレートの配列順がそのまま列順になる。** 順序は §8-1（値が期待する列・行に入ること）の contract そのものなので、テンプレート内で欄を並べ替えると列も動く。これは意図した挙動で、様式ごとの列構成をテンプレート側で決められるということでもある。

管理6列だけは様式に依存しないためコード側に固定で持つ: 要確認セル数／最低信頼度／帳票ID／入力ファイル名／ページ番号／ステータス。

**v1 の期待値と検証**

現行テンプレートから導出すると次になる。

| 範囲 | 列番号 | 列数 | 導出元 |
|---|---|---|---|
| 管理 | 1〜6 | 6 | 固定（様式非依存） |
| 本人 | 7〜20 | 14 | `front.fields[]` が14要素 |
| 家族欄 | 21〜80 | 60 | `front.tables[family]`: (5+5)行 × 4列（うち生年月日は subfields で3列に展開）|
| 明細 | 81〜220 | 140 | `back.tables[detail]`: **(14+14)行** × 5列（自作サンプルの罫線を射影実測・2026-08-27）|

合計 6+14+60+140 = **220**。`v1.8` までの209は明細13行想定・郵便番号1列の机上の数字で、実測により改めた。

**220 は決め打ちの入力ではなく導出の結果。** 実際、テンプレートを実測に合わせた時点で導出が 209→220 へ追従した——列リストをコードへ持っていたら3箇所同時修正だった。要件 §5.6（220列・v3.10）に合わせ、v1 は**起動時に導出結果が220列であることと、列名が期待どおりであることを検証し、不一致ならテンプレートを拒否する**。テンプレートの編集ミスで列構成が黙って変わる事故を、単一の真実（テンプレート）を保ったまま防ぐ。汎用化の段階でこの検証を外せば、様式ごとに列数が変わる形へそのまま移行できる。

**本人13列**（列7〜19）

`person_電話番号` / `person_ふりがな` / `person_氏名` / `person_生年月日_元号` / `person_生年月日_年` / `person_生年月日_月` / `person_生年月日_日` / `person_郵便番号1` / `person_住所1` / `person_郵便番号2` / `person_住所2` / `person_会社名屋号` / `person_所在地` / `person_備考`（列順はテンプレートの定義順＝帳票の物理配置順）

要件 §3.1 の本人7項目を列へ割ると14列になる。**住所2段は各段が独自の郵便番号欄を持つ**（自作サンプル実測）ため郵便番号は2列。住所2段の意味は Q-04 が未回答のため、`1`＝上段・`2`＝下段として位置で割り当てる ※解釈。

**家族欄6列**: `続柄` / `氏名` / `生年月日_元号` / `生年月日_年` / `生年月日_月` / `生年月日_日`——ただし物理欄は4つで、**生年月日は1セルへ「7.7.20」とまとめ書きされる**（実測）。テンプレートでは `subfields: [年,月,日]` を持つ1列とし、読取値を機械分割して3出力列へ展開する（D-23）
**明細5列**: `来店年月日_年` / `来店年月日_月` / `来店年月日_日` / `金額` / `品目`——こちらは物理的に3サブセルへ分かれている

**列ヘッダ**: 管理列は上表の日本語名をそのまま使う。抽出対象列は **field_id と列ヘッダを同一**にする（`family_01_続柄` など）。1行目がヘッダ、2行目以降がデータ。

**要確認セル数の範囲**: 抽出対象は列7〜220、Excel の列文字では `G`〜`HL`。データ行 n の数式は `=COUNTIF(Gn:HLn,"〓")`。管理列は範囲に含めない（要件 §5.6）。`"〓"` にワイルドカードが無いため COUNTIF はセル全体の完全一致で数える。

**最低信頼度**: 数式ではなくツールが計算した静的な値を書く。母集団は「〓でも空文字でもなく、項目種別が `text` のセル」。`choice` のセルは自前スコアであって OCR の信頼度ではないため含めない（要件 §5.6）。該当セルが1つもない行は空欄。

### 4.4 中間データ（SQLite）

| テーブル | 主キー | 主なフィールド |
|---|---|---|
| `page` | `page_id` | `source_file` `page_no` `state` `status` `attempt` `image_path` `unassigned_below_table` `unassigned_other` `updated_at` — UNIQUE(`source_file`,`page_no`) |
| `token` | (`page_id`,`seq`) | `face` `text` `conf` `x` `y` `w` `h` |
| `cell` | (`page_id`,`field_id`) | `raw_text` `conf` `kind` `is_empty_row` |
| `alignment` | (`page_id`,`face_id`) | `transform`（JSON文字列） `ok` `geometry_hash` |
| `era_score` | (`page_id`,`field_id`) | `scores`（JSON文字列） |
| `run` | `run_id` | `started_at` `config`（JSON文字列） |

- 書き込みは **UPSERT**（`INSERT ... ON CONFLICT DO UPDATE`）。DELETE→INSERT にすると、その間の中断で中間状態が残る（実装レビュー M1）
- 接続時に `PRAGMA journal_mode=WAL` を設定する。既定の DELETE モードだと `run` 実行中に別ターミナルで `status` を叩いて `database is locked` になる（実装レビュー S1）
- **`api_call` テーブルは作らない。** 送信回数の累計は `page.attempt` の合計で足りる。一度きり運用でテーブルを1つ減らす利点の方が、何回目の送信で失敗したかを追える価値より大きい（実装レビュー「問い1」への回答）
- **`placement` テーブルも作らない。** 配置誤りの自己検出（D-15）を1方式に絞ったため、検証器ごとの行を持つ必要がない（§9 D-15）
- JSON 列（`transform` `scores` `config`）は TEXT に JSON 文字列として入れ、Python 側で `json.loads` / `json.dumps` する。SQL から中身を検索する要求がないため JSON1 拡張は使わない
- `page.state` は処理の進行、`page.status` は出力に書く8種。**別物として持つ**
- **`era_score` に判定結果（`decided`）を持たない。** 丸印閾値は設定値であり、変えたら判定が変わる。判定結果を永続化すると閾値を変えても古い値が残り、§3.2 の「閾値の適用は `render` 時」という設計と矛盾する。`scores` だけを持ち、5値への変換は毎回そこから導出する。要件 §5.4 の「未選択・判定不能を中間データで区別して保持」は、`scores` と閾値から両者を復元できることで満たす
- **`page.unassigned_*` を2つに分ける。** テーブル領域の下端より下にある枠外 word（`unassigned_below_table`）と、それ以外（`unassigned_other`）。行数超過（D-06）と様式不一致（D-15）が同じ数字を奪い合わないようにするため。理由は §6.4
- **`alignment.geometry_hash`** はテンプレートの幾何セクションのハッシュ。`remap` が token 座標を無効化する変更を検出するために持つ（§6.7）

`state` の値: `pending` → `expanded` → `aligned` → `sending` → `received` → `mapped` → `done`。失敗時は `failed`。

**再開規則**: `state != 'done'` のページのみ再処理する。`state = 'sending'` のページは送信済みか不明なため1枚だけ再送を許容する（D-05）。

### 4.5 セルの3状態とステータス

**セルの3状態**（要件 §5.5）

| 状態 | 出力 | 要確認セル数 | 条件 |
|---|---|---|---|
| 読取値 | 文字列 | 加算しない | 信頼度が閾値以上 |
| 〓 | `〓` | **加算する** | 信頼度が閾値未満／記入行なのに読取結果が空／選択式で未選択・判定不能 |
| 空文字 | `""` | 加算しない | **空行と判定された行のみ** |

記入行の未読取を空文字にしない。空文字が現れるのは空行だけとし、「未記入」と「読めなかった」を混ぜない。

**ステータス8種**（要件 §5.6）。複数該当は `;` で連結し、失敗系を先に置く。連結時の並び順:

```
展開失敗 → 位置合わせ失敗 → 様式不一致 → 送信失敗
       → 未処理（送信上限到達） → 未処理（中断） → 超過あり
```

`正常` は他と併記しない（単独でのみ出る）※解釈。

## 6. 各処理の設計

### 6.1 取り込み・PDF展開

- 対象拡張子: `.pdf` `.jpg` `.jpeg` `.png`。それ以外はスキップしログへ記録
- PDF は `pdftoppm -r <render_dpi> -png` で1ページずつ PNG へ展開する。1ページ＝1帳票
- Poppler の実行パスは開発環境と配布後で解決方法が変わる。`.bat` の PATH 設定には頼らない（実装は §12-C1）
- 展開に失敗したページは `status=展開失敗` の全〓行として出力し、次へ進む
- **帳票ID**: `<入力ファイル名のstem>_p<4桁ページ番号>`。氏名を含めない（要件 §5.6）。stem が衝突する場合は入力パスの SHA-1 先頭8桁を付ける

### 6.2 表裏分割と位置合わせ

面ごとに独立して補正する。1枚全体への単一変換は不可（要件 §5.2）。

**除外領域を2パスで当てる。** テンプレートの除外矩形は位置合わせ**後**の面ローカル座標（§4.2）だが、二値化と角度推定は位置合わせ**前**の画像で行う。同じ矩形をそのまま当てると傾きのぶん位置がずれ、黒塗りが Otsu の母集団に残る。綴じ穴帯は端の帯なので多少ずれても影響は小さいが、中央寄りの黒塗りはヒストグラムを歪める。

| パス | 使う矩形 | 目的 |
|---|---|---|
| 粗（補正前） | 除外矩形を M ピクセル膨張させたもの | 二値化閾値の決定と角度推定から外す |
| 本（補正後） | 除外矩形をそのまま | 抽出対象外の確定・丸印判定・トークン割付から外す |

膨張量は想定する最大傾きから出す。`M = ceil(D × sin(θmax))`（D = 面の対角長の半分、θmax = 想定最大傾き）。面が 2480×1754・θmax = 2° なら D ≈ 1518、M ≈ 53 となるので 60 を採る ※解釈。θmax は Q-03 で実物のスキャン品質が判明した時点で見直す。綴じ穴帯の膨張はページ内側方向のみでよい。

1. 展開画像を `image.width` × `image.height` へ正規化し、`faces[].source.rect` で面画像を切り出す（v1 は上下2面）
2. グレースケール化
3. **粗マスク**: 膨張させた除外矩形の画素を、以降の閾値計算と角度推定の母集団から外す（要件 §5.2「二値化閾値の決定にも用いない」）
4. 二値化（Otsu・粗マスク後の画素のみで閾値を決める）
5. 主要角度を推定して回転補正する。Hough 直線から水平成分の角度中央値を採る
6. 面の寸法を `source.rect` の `w` × `h` へ戻す。回転補正で外接矩形が広がるため、§4.2 の面ローカル空間に合わせ直す
7. **本マスク**: 補正後の画像へ膨張なしの除外矩形を当て、抽出対象外を確定する
8. 補正後の2面を縦に再結合し、送信用の1枚を作る（§3.3 F5）

- 角度推定が収束しない・直線が検出できない → `status=位置合わせ失敗`。この判定は F4 の時点で下せる
- 枠外トークン率が閾値超（§9 D-15）→ `status=様式不一致`。**これは割付（F7）の後でしか判定できない**ため、`run` は送信まで進んでから倒れる。母集団は `unassigned_other` のみを使う（§6.4）
- どちらも全〓行として出力し、次のページへ進む

`Aligner` を Protocol にするのは、実物のスキャン品質（Q-03）次第で方式を替える余地を残すため。二値化済み・低dpi だった場合は手順3〜4が成立しない。

### 6.3 Vision 送信と再試行

- 機能種別は **`DOCUMENT_TEXT_DETECTION` で確定**（M0-S2 実測・2026-08-27）。`full_text_annotation` の階層（page > block > paragraph > word > symbol）から word 単位の confidence を取る。実測値: 自作サンプル1ページで word n=164・confidence 0.329〜0.998 の連続分布・zero率0%（`spikes/s2_vision_confidence.py`）。**`TEXT_DETECTION` は word/symbol とも全語 0.0 で使用不可**、`text_annotations` 経由も DOCUMENT で 0.0——confidence は `full_text_annotation` からのみ取れる
- 言語ヒント `ja`
- 1リクエスト＝1画像＝1リトライ単位（要件 §5.3）
- **クライアント内蔵のリトライを明示的に無効化する。** `google.api_core.retry.Retry` が既定で効くと自前の指数バックオフと二重になり、待ち時間が伸びてリトライ回数の管理が二重帳簿になる ※要検証（実装レビュー S2）
- 自前バックオフ: 初回1秒から倍化、最大5回（定数）。超過は `status=送信失敗` を記録して次へ
- 送信枚数上限（設定値）に到達したら送信を止め、未送信分は `status=未処理（送信上限到達）` の全〓行として出力する。次回実行の対象として残す

> 設計の最大リスクだった「confidence が取れない場合」は **M0-S2 の実測で解消した**（上記）。〓判定・最低信頼度列・要確認セル数の根拠が立った。

### 6.4 トークン割付

- **symbol（1文字）単位の中心点**がどのテンプレート矩形に入るかで割り当てる。当初案は word 単位だったが、S2 トークンのドライラン（2026-08-27）で **Vision が明細の年|月|日セルを跨いで数字を1word に結合する**実例が出た（「10 8 31 1000」→1word「108311000」が日セルへ着地＝日付と金額の混線）。symbol は個々に外接矩形と confidence を持つ（S2 実測 n=322）ため、文字ごとに物理位置で振り直せば結合の影響を受けない
- 中心点を採るのは、枠を跨いだ記入が隣接欄へ二重に入るのを防ぐため ※解釈
- 1つの矩形に入った symbol は y → x の順に並べて連結する。日本語のため区切り文字は入れない
- 項目の信頼度は、その矩形に入った symbol の confidence の**最小値**（要件 §5.5 の「複数語は最小値」を symbol 粒度で適用。1文字でも怪しければ〓へ倒す）
**枠外 word を2つに分けて数える。** どの矩形にも入らなかった word を `page.unassigned_below_table` と `page.unassigned_other` へ振り分ける。

振り分けは**ブロック単位**で判定する。テーブルは面をまたいで2つあり（表面の家族欄・裏面の明細）、さらに各テーブルが左右2ブロックを持つため、「テーブル領域の下端」を1つに決められない。ある word が、**同じ面のいずれかの `tables[].blocks[]` について「そのブロックの最終行の下端より下」かつ「そのブロックの列範囲（`origin.x` から最終列の右端まで）の内側」**に入れば `unassigned_below_table`、どのブロックにも当てはまらなければ `unassigned_other`。両者の合計が枠外 word の総数になる。

分ける理由は、D-06（行数超過）と D-15（様式不一致）が同じ数字を取り合うため。家族欄や明細が定義行数を超えて記入されたページは枠外 word が増えるので、1つの数字で両方を判定すると**枠外トークン率が D-15 の閾値を超え、本来「超過あり」で出したいページが「様式不一致」＝全〓に食われる**。データが取れているのに捨てることになる。

| 判定 | 使う値 | 出力 |
|---|---|---|
| D-06 行数超過 | `unassigned_below_table` が3個以上 | `status=超過あり`（値は出す） |
| D-15 様式不一致 | `unassigned_other` ÷ 全 word 数が閾値超 | `status=様式不一致`（全〓） |

D-15 の母集団から `unassigned_below_table` を外すのが要点。両方が成立した場合はステータスを `;` で連結し、§4.5 の並び順に従って様式不一致を先に置く。

### 6.5 〓判定・空行判定・金額正規化

**空行判定**: テーブルの1行分の **`kind=text` の列**に symbol が1つも入らなければ空行とする（要件 §5.5 の「行内全欄」を text 列に限定 ※解釈）。choice 列を母集団に入れると、**印字の昭平令が必ず読まれるため空行が一つも存在しなくなる**（ドライランで全10行の元号セルに印字が載ることを確認）。空行の列は全て空文字、丸印判定も行わない、要確認セル数に加算しない。インク量を測る画像処理は実装しない。

> 判定が Vision の読取結果に依存するため、かすれ・薄い記入を空行と誤判定するリスクが残る。要件 §8 第2層の残存リスクとして受容する。

**〓判定**（`render` 時に適用する。cell には焼き込まない）

```
行が空行            → 全列 空文字
セルに word が無い  → 〓
信頼度 < 〓閾値     → 〓（読取値は出力に残さない）
選択式で未選択/判定不能 → 〓（中間データでは両者を区別して保持）
それ以外            → 読取値
```

**金額正規化**（D-01 の適用順）

```
1. 前後の空白を除去する
2. 全角数字・全角記号を半角へ統一する
3. 区切り候補（、／，／半角空白）を , へ置換する
4. 区切りを含まない  ^\d+$        → そのまま整数化する
5. 区切りを含む      ^\d{1,3}([,.]\d{3})+$ に合致 → 区切りを除去して整数化する
6. 上記以外（単位付き・非数値・不正な区切り）  → 〓
```

手順4は ※解釈。要件 §5.5 は「`^\d{1,3}([,.]\d{3})+$` に合致する場合のみ桁区切りとみなし除去・整数化。非合致・非数値・単位付きは〓」と書いており、文言どおりに読むと区切りを含まない `100` も〓になる。区切り記号を含まない純数字を〓へ落とすのは初穂料の実額として不自然なため、本設計では手順4を置いた。**ユーザー確認が要る**（金額の実在レンジは要件レビュー r2 §7-8 で未回答）。

金額以外は**記載されたまま転記する**。推定・西暦変換・辞書置換・前行継承をしない（要件 §5.5）。明細の年は `H20` `R3` `7` をそのまま出す。

### 6.6 出力

`.xlsx` と `.csv` を**同一の cell 集合から同一タイムスタンプで同時に生成する**。形式の選択制ではない（要件 §5.6）。

**.xlsx**

- 1行目にヘッダ、2行目以降にデータ
- 金額列のみ数値型。それ以外の全列を文字列型（`number_format='@'`）にして先頭ゼロを保持する
- 〓セルへ条件付き書式（背景色）。範囲 `G:HL` に「セルの値が `〓` に等しい」ルールを1つ置く。ワークシートレベルの設定なので行ごとに設定しない
- 要確認セル数は `=COUNTIF(Gn:HLn,"〓")`。修正のたびに自動で減る
- **書き込み方式は `write_only=True` で確定**（M0-S1 実測・2026-08-27・`spikes/s1_openpyxl_writeonly.py`）。3行×4列の極小ブックで、先頭ゼロ保持（`number_format='@'`）・金額の数値型・COUNTIF 数式・ワークシートレベルの条件付き書式が読み戻しまで含めて全て成立した。220列は `WriteOnlyCell` でラップし、行カウンタを自前で保持する（§12-C2）

**.csv**

- 全列をクォートし、BOM 付き UTF-8 で書く
- 要確認セル数は数式ではなく静的な数値
- Excel で直接開くと型推論で先頭ゼロが失われるため、**先頭ゼロの確認はファイル内容をテキストとして読んで行う**（要件 §5.6・§8-12）

**出力先と命名**: 設定または GUI で選んだフォルダへ `output_YYYYMMDD_HHMMSS.xlsx` / `.csv`。GUI で選んだ値は設定ファイルへ保存し次回の既定値にする。衝突時分岐・実行時のファイル名指定・接頭辞接尾辞は設けない（要件 §5.7）。

秒まで含めるのは、分単位だと同一分内の `render` 2回で衝突するため。要件 §5.7 の `output_YYYYMMDD_HHMM` は「例:」であり、拘束するのは「同名衝突を発生させない」の方。

`OutputWriter` を Protocol にするのは、列構成の差し替え（要件 §9）を塞がないため。v1 は220列固定の実装1つだけを持つ。

### 6.7 再開・再出力

| 操作 | 読む | 書く | API |
|---|---|---|---|
| `run` 再実行 | `page.state != 'done'` | token / cell / `era_score` / `page.status` / 出力 | する |
| `remap` | token / 展開画像 / `alignment.transform` | cell / `era_score` / `page.status` / 出力 | しない |
| `render` | cell / `era_score` / `page.status` | 出力 | しない |

`render` が `era_score` を読むのは、5値への変換を毎回 `scores` から導出するため（§6.8）。ここを落とすと丸印閾値を変えても元号列が変わらない、あるいは元号列が空で出る。

`remap` が展開画像と `alignment.transform` を読むのは、`choice_marks` が幾何セクションの外にあるため。テンプレートで丸印の矩形を動かしたら環状帯スコアを取り直す必要があり、それには面画像が要る。保存済みの transform を展開画像へ再適用して面を作り直す（位置合わせのやり直しではない）。

**`remap` はテンプレートのどの変更でも使えるわけではない。** token の座標は、旧テンプレートの `render_dpi`・`image`・`record`・`faces[].source`・`exclusions` の5つで行った位置合わせの産物。これに `face_id`（`token.face` と `alignment` を結ぶキー）を加えた6要素を変えると token が使えなくなり、`remap` では直せず `run`（API 再送信）が要る。`face_id` を含めるのは、改名すると `token.face` が旧名を指したまま残り、**照合が空振りしてセルが黙って空になる**ため。

| テンプレートの変更箇所 | token への影響 | 必要な操作 |
|---|---|---|
| `render_dpi` / `image` / `record` / `faces[].source` / `face_id` / `exclusions` | **座標が無効になる** | `run`（再送信・課金あり） |
| `fields[].rect` / `tables[]`（`blocks`・`row_pitch`・`columns`） / `field_id` / `kind` / `choice_marks` | 影響なし | `remap` |

上段の6要素を**幾何セクション**と呼び、正規化した JSON の SHA-256 を `alignment.geometry_hash` へ保存する。`remap` は実行前に現テンプレートのハッシュと突き合わせ、**不一致なら処理せず「`run` が必要」と告げて終了する。** この歯止めがないと「テンプレートをいじったら remap すれば API 再送不要」と読めてしまい、座標のズレたまま全ページを再割付する——要件 §8 第1層（配置誤りは1件でも不合格）に直撃する壊れ方をする。

**ステータスが確定する段**: 展開失敗・位置合わせ失敗・送信失敗・未処理系は `run` 時。様式不一致（D-15）と超過あり（D-06）は割付の産物なので `run` と `remap` 時。`render` は `page.status` をそのまま出すだけで判定し直さない。

- **入力ページ数＝出力行数**を処理の成否によらず常に維持する（要件 §3.4）。失敗したページも全〓行として1行出す
- 同一の中間データ・同一設定での再出力結果は完全一致する（要件 §6.2）。乱数・時刻に依存する処理を出力経路へ入れない
- 中断のトリガはプロセス終了（Ctrl+C）と GUI の中断操作の2つ。**どちらも同じ結果**にする——`status=未処理（中断）` の全〓行を出し、次回続行する（要件 §5.8）
- **Ctrl+C の伝播は実機確認が要る** ※要検証。Windows のコンソールイベントは SIGINT と挙動が異なり、`.bat` 経由の子プロセス（exe、さらに `pdftoppm`）まで届くかは未検証（実装レビュー S7）。M3 の早い段階で「`run` 実行中に Ctrl+C」を試し、`state=sending` で正しく止まることを確認する

### 6.8 元号丸印判定

印字された「昭・平・令」を手書きの丸で囲む方式。判定箇所は本人1＋家族欄各行の最大11箇所。

1. テンプレートの `choice_marks` から各選択肢文字の矩形を取る
2. 文字の外接矩形の**外側からセル境界までの環状帯**を切り出す。単純減算だと位置合わせ誤差が印字漢字の残差として出るため、判定領域を環状帯に限定する
3. 環状帯のインク画素比をスコアとする
4. 5値へ落とす

```
最大スコア < 丸印閾値          → 未選択      （帳票の事実）
上位2つの差 < 判別閾値         → 判定不能    （ツールの能力限界）
それ以外                       → 昭 / 平 / 令
```

**永続化するのは `scores` だけ。** 5値への変換は `render` 時に毎回 `scores` と閾値から導出する。丸印閾値は設定値なので、判定結果を保存すると閾値を変えても古い値が残り、§3.2 の「閾値の適用は `render` 時」という設計と矛盾する。

未選択と判定不能は**出力上どちらも〓**だが、業務上の意味が違う（前者は帳票の事実、後者はツールの能力限界）。要件 §5.4 の「中間データでは区別して保持」は、`scores` と閾値から両者を復元できることで満たす——`status` サブコマンドや診断出力ではこの区別を出せる。空行と判定した家族欄行には判定を実行しない。

**退避先**: 検証の結果いずれの方式も成立しない場合、元号セルを一律〓としてリリースしてよい（要件 §5.4）。列構成は変わらず、目検で補完する。**丸印判定の成立をリリース前提にしない。**

Q-07（大正・明治生まれの記載方法）は未回答。印字選択肢に無い元号が書かれていた場合、環状帯スコアは全て閾値未満となり「未選択」＝〓へ落ちる。誤った元号を出すよりは安全側に倒れるため、回答前でも実装を進められる。

### 6.9 枠候補の生成（`detect-grid`）

テンプレート編集画面へ枠候補を返す。**生成器を2つ持ち、`GridSource` Protocol で差し替える。**

| 生成器 | 入力 | Q-03 依存 |
|---|---|---|
| `RuledLineGrid`（罫線の自動検出） | 面画像 | **する。** 実物が二値化済み・低dpi だと不成立になりうる |
| `UniformGrid`（等分割生成） | 外枠の矩形＋行数＋列数 | しない |

**`RuledLineGrid` の手順**

1. 面画像を二値化する（§6.2 の本マスク後の画像を使う。除外領域は母集団から外れている）
2. 長い水平カーネルでモルフォロジー開演算 → 水平罫線。垂直カーネルで同様 → 垂直罫線
3. 各方向の罫線を軸へ射影し、ピークの位置を線の座標とする
4. かすれ・欠損は、検出済みの線から等間隔補間で補う
5. 水平線と垂直線の交点からセル矩形を組む

**`UniformGrid` の手順**: 外枠を行数・列数で等分割する。列境界は利用者が後からドラッグで動かせる。

**どちらの出力も同じ形にする**——セル矩形の配列と、それを `tables[]` 定義（`origin`・`row_pitch`・`row_height`・`columns[]`）へ当てはめた結果。編集画面は生成器の違いを知らない。

**検出結果をテーブル定義へ当てはめる。** 検出した行の間隔は実物ではわずかにばらつくため、最小二乗で `row_pitch` を1つに畳む。**当てはめの残差（最大ずれの px）を返し、画面へ出す**——残差が大きいときは検出が失敗しているので、利用者が等分割生成へ切り替える判断材料になる。テンプレートに保存されるのは畳んだ後のテーブル定義であって、検出した個々の矩形ではない（§4.2 のスキーマは変えない）。

**行ピッチのドリフトが起きないことがこの節の要点。** 人がドラッグで枠を引くと 1px の誤差が13行目で13px になり、行高 56px 規模の欄では隣接行へ食い込む。要件 §8 第1層（行ズレは1件でも不合格）を人手の精度に賭けないために、行位置は算術か検出から決める。

**退避先**: `RuledLineGrid` が実物で不成立でも、`UniformGrid` があればテンプレートを作れる。要件 §5.10 が「自動検出の成立をリリース前提にしない」と定めており、元号丸印判定（§6.8）と同じ扱いにする。

**v1 で検証できる範囲の限界**: Q-03 が未入手のため、`RuledLineGrid` は**自作サンプルでしか試せない。** 自作サンプルは罫線が完全なので必ず通り、それは実物での成立を意味しない。実物到着後に閾値・カーネル幅の再調整が要る前提で作る（要件 §9）。

### 7.1 実行画面（M5）

最小構成の6機能: 入力フォルダ選択／出力先選択／実行開始／進捗表示／完了サマリ表示／出力フォルダを開く。

完了サマリの6項目は要件 §5.9 と同一——処理枚数／出力行数／位置合わせ失敗枚数／API送信回数／要確認セル数総計／行数超過件数。

【Should】標準構成（設定画面・一時停止と中断ボタン・エラー一覧表示）は最小構成が動いてから足す。

起動時に資格情報の存在と読取可否を検証し、不備なら開始せず対処方法を画面へ出す。**資格情報の値はメッセージ・ログ・画面のどこにも出さない**（要件 §5.3）。

### 7.2 テンプレート編集画面（M6・D-22）

要件 §5.10 の7項目を canvas 上で実装する。

| # | 機能 | 実装 |
|---|---|---|
| ① | 画像の表示（ズーム・パン） | canvas へ描画。PDF はコアでPNG化してから読む |
| ② | **枠候補の生成** | コアの `detect-grid` を呼ぶ（§6.9）。罫線の自動検出と等分割生成の2択。画面は画像処理を持たない |
| ③ | **枠のクリックで抽出対象／対象外を切替** | 生成された枠をクリックしてトグル。ドラッグでの矩形作成・移動・リサイズも併用できる |
| ④ | 項目名と項目種別の割り当て | 選択中の矩形に `field_id` と `kind`（text / choice）を設定 |
| ⑤ | 除外領域の指定 | 矩形を `exclusions` として登録 |
| ⑥ | 表裏分割位置の指定 | 水平線1本のドラッグ |
| ⑦ | 列位置の表示 | **読み取り専用。** `field_id` から §4.3 の列番号を引いて表示するだけ |
| ⑧ | JSON の読み込み・保存 | §4.2 のスキーマをそのまま読み書き |

**②③が中核。** 枠を人がドラッグで引くのではなく、**生成してからクリックで選ぶ**。行位置が算術または検出から決まるため行ピッチのドリフトが起きない（§6.9）。ドラッグでの作成は単発欄と、生成結果の微修正に使う。

`detect-grid` は当てはめ残差を返す（§6.9）。**残差が大きいときは画面に警告を出し、等分割生成への切り替えを促す。** 自動検出が黙って失敗したまま進むのが一番まずい。

⑦は表示だけで、どの項目をどの列へ出すかを画面で組み替える機能は持たない（要件 §3.3）。**画面が持たないのは列割当の変更だけ**——罫線の自動検出は要件 v3.8 で v1 スコープへ入り、②が担う。

**この画面が行うのはテンプレート JSON の読み書きと画像表示だけ。** OCR・位置合わせ・丸印判定を画面側で実行せず、中間データ・出力ファイルも書き換えない（要件 §5.10）。

**未保存時の確認**: 未保存の編集がある状態で「画面を閉じる」「別の画像を読み込む」「別のテンプレートを開く」操作をした場合、破棄してよいかの確認を出す。自動保存はしない（要件 §5.10・v3.7 追加分）。

**操作の詳細は書かない**（§2）。ハンドルの当たり判定・テーブル定義モードの入力順・キーボード操作・スナップの有無は、文書で詰めるより実際に触って直す方が速い領域なので M6 の実装中に決める。この節が定めるのは**何ができる画面か**と**何をしない画面か**まで。

保存する JSON は `template.schema.json`（§4.2）で検証してから書き出す。検証を通らない状態では保存させない。

### 7.3 コアとの進捗受け渡し（D-16）

Python コアが **stdout へ JSON Lines**（1行1イベント）を出し、Tauri が sidecar の stdout を読んでパースする。

```
{"event":"start","total":100}
{"event":"page","page_id":"scan001_p0003","status":"正常","done":3}
{"event":"summary","pages":100,"rows":100,"align_failed":2,"api_calls":98,"unclear_cells":417,"overflow":1}
```

この方式を採る理由は3つ。追加の依存（IPC・ローカルソケット・一時ファイル）が要らない。CLI 単体で実行したときも同じ出力が人に読める。ログ（`app.log`）とはストリームが分かれるため、ログの型制約（§8）を素通りしない。

**イベントに帳票の記入値を入れない。** ログと同じ制約をここにも適用する。

## 8. ログ・資格情報・個人情報保護

### 8.1 ログ

`app.log`（操作・実行設定・処理結果・警告・回復処理）と `error.log`（エラー・失敗内容）の2本。実行開始時に主要設定値を記録する。

**帳票の記入値は一切書かない。** 出力してよいのは 入力ファイル名・ページ番号・帳票ID・項目ID・処理ステップ名・エラーコード・信頼度の数値・設定値 に限る。例外メッセージに変数値を含めない（要件 §5.9）。

実装の担保:

- `logging_safe.py` が `import logging` する唯一のモジュールにする。他モジュールからの直接 import を**レビュー項目として明文化する**。型だけでは `logger.info(f"value={cell.raw_text}")` のようにフィールドを取り出す書き方を防げないため、型制約とレビューの両方で守る（実装レビュー S3）
- 記入値を持つクラスの `__repr__` は**クラス単位で固定文字列**を返す（`f"<{type(self).__name__} field_id={self.field_id} redacted>"`）。フィールド単位の `field(repr=False)` はフィールド追加時の付け忘れが構造的に残るため採らない（実装レビュー S4）
- **Poppler の stderr をそのままログへ渡さない。** 固定のエラーコードへ変換してから渡す。生の stderr は型で守っている構造の抜け道になる（実装レビュー S5）

### 8.2 資格情報

Vision API の資格情報を平文で保存しない。OS 資格情報ストアまたは DPAPI で保護する（要件 §3.5）。

認証方式は **DPAPI によるファイル暗号化で確定**（M0-S3 実測・2026-08-27・`spikes/s3_keyring_size.py`）。実物のサービスアカウント JSON（2,366 bytes）を `keyring.set_password()`（WinVaultKeyring）へ入れると **CredWrite エラー1783 で失敗**——Windows 資格情報ストアの blob 上限に掛かり、丸ごと保存は成立しない（実装レビュー M4 の懸念が的中）。実装は「JSON を DPAPI（`CryptProtectData`・CurrentUser スコープ）で暗号化したファイルとして保持し、実行時に復号してクライアントへ渡す」。平文の JSON は取り込み後に利用者へ削除を促す。

`verify` サブコマンドで資格情報の読取可否と Poppler の実行可否を確認できるようにする。Poppler は存在確認だけでなく `pdftoppm -v` を実際に起動して判定する。

### 8.3 中間データの保護

中間データは記入値（個人情報・要配慮個人情報）を含む。クラウド同期対象外のローカルパスに置き、削除は `purge --yes` の明示操作のみで行う。正常完了後も保持する（要件 §6.3）。

**アプリ側の暗号化は行わない**（D-07）。理由: 鍵の保管場所が同じ端末になるため、実行端末のディスク暗号化を超える保護にならない。かわりに保持先をクラウド同期対象外パスへ限定し、明示削除の経路を用意する。実行端末のディスク暗号化の状況（Q-21）が判明した時点で再判断する。

開発・単体検証は無記入原本と自作サンプルのみで行う。実データは指定端末のみで扱い、検証後に削除する（要件 §6.5）。

## 11. テスト方針

網羅的なテスト設計書は作らない。**背骨を1つ決めて、そこに寄せる。**

**背骨は再現性。** 要件 §6.2 が「同一の中間データ・同一設定での再出力結果が完全一致すること」を求めており、これは自動化しやすい性質でもある。固定した中間データ（SQLite ファイル）と固定した設定から `render` を2回走らせ、生成物をバイト単位で比較する。ゴールデンファイルを1つ置いて差分ゼロを回帰テストにする。ここが緑なら、出力層のリファクタで壊れたことに気づける。

そのうえで、要件 §8 の合格条件に直結する検証を3つ置く。

| 対象 | やり方 | 対応する合格条件 |
|---|---|---|
| 第1層（配置） | 記入内容が既知の自作サンプルで、期待する列・行に値が入るかを表で突き合わせる。Vision の読取精度に依存しないため決定論的に判定できる | §8-1・§8-2 |
| テンプレート往復 | エディタが書いた JSON → `template.schema.json` で検証 → コアが読む → 展開した field_id が §4.3 の203列と過不足なく一致 | §8-14 |
| 出力の2形式一致 | 同一実行の .xlsx と .csv で、管理列を除く抽出対象列の値が一致。CSV の先頭ゼロは**ファイル内容をテキストとして読んで**判定する（Excel で開いた表示では判定しない） | §8-12 |

**Vision の呼び出しはモックにする。** 実 API を叩くテストは置かない——課金が発生し、応答が非決定的で、再現性の背骨と両立しない。実測は M0-S2 のスパイクと M7 のパイロットで行い、テストスイートには入れない。

ndarray を含むデータクラスの比較は `==` では書けない（§12-C3）。配列部分は `np.testing.assert_array_equal` で別途比較する。
