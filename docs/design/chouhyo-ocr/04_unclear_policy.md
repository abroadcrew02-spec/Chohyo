## 3. 参照先（fallback）の新仕様

### U-02: 参照先は「主が空のときだけ有効な受け皿」

現行は参照先を常時アクティブな受け皿として割り付け、後から採否を決めていた（`mapping.py:215-226`）。採用しない場合に `fb` の中身が再代入されず消える——これが #54(a)。

新仕様では**採用しないと決まった時点で、参照先はその欄の受け皿ではなかったことにする**。参照先に落ちていた文字は未割付の文字と同じ扱いに戻し、§5 の穴判定 → 枠外判定を順に通す。

これが正しい理由は実測で示せる。出荷テンプレでは `person_郵便番号1` の参照先(651,308,478,60)が `person_住所1` の外接矩形の穴(649..1129, 310..368)とほぼ一致する（§1.2・§1.3）。つまり:

- 郵便番号の主が空（＝〒を住所行に書いた）→ 参照先が有効 → その文字は郵便番号の値。住所欄の穴には「他の受け皿に属さない文字」が0字なので住所は〓にならない（実測どおり）
- 郵便番号の主に記入あり（＝〒を専用枠に書き、住所が左へ食い込んだ）→ 参照先は無効 → 食い込んだ文字は住所欄の穴に落ちる → **住所欄が〓になる**

#54(a) が報告した「東京都…が都…になる」経路で、値を失った当の欄（住所）が〓になる。郵便番号は正しく読めているので〓にしない。「誰が壊れたか」と「誰に〓を立てるか」が一致する。

### U-03: 「主が空」の3分岐

```
NOISE_MAX = 1   # 罫線の掠れ・句点・隣欄からのはみ出しは1文字単位で入る。
                # 2文字以上の連なりは記入とみなす。※実データでの較正は未実施
n_main == 0 かつ n_fb >= 1                 → 参照先を採用（判定表 #9）
1 <= n_main <= NOISE_MAX かつ n_fb >= 2    → 矛盾。欄を〓（判定表 #8・値は主のまま保存）
それ以外                                    → 主を採用（参照先の文字は A へ）
```

矛盾を参照先採用に倒さない理由: 主の1文字が本物の値（1文字の記入）である可能性を排除できない。参照先を採ると誤転記になる。〓なら人が紙を見て決められる。空欄を出すコスト＜誤った値を出すコスト。

`NOISE_MAX` は信頼度ではなく構造の判定なので `config.json` には出さず `mapping.py` の定数に置く（設定6項目・要件 §5.8 を増やさない）。

**この修正で解決しないこと**: 「7桁のうち4桁だけが主枠に入り、残りが右隣の欄へ溢れる」型の部分値。実測すると `person_郵便番号1` の主枠(y361..439)から右へ溢れた文字は参照先(y308..368)ではなく `person_住所1` の主 rect(y368..439)に入る。したがって参照先の仕組みでは検知できない。一般の「隣の欄への溢れ」検知には行の連続性推定が必要で、正常に隣り合う記入との区別が付かず誤検知が多い——誤検知の多い〓は現場の〓不信を招くため今回はやらない（§12・別 issue 提案）。

### U-04: 由来印

| 層 | 表現 |
|---|---|
| 中間データ | `cell.origin TEXT NOT NULL DEFAULT ''`。値は `''`（主）／`'fallback'`（参照先採用）／`'conflict'`（判定表 #8） |
| xlsx | 参照先採用セルに**静的な背景色**（`FILL_FALLBACK = "E8F4FA"` 淡い青）。値は書き換えない（転記主義）。〓の条件付き書式が同じセルに掛かった場合は条件付き書式が優先し、〓色で表示される（〓の方が優先度の高い情報なので許容） |

## 4. U-06: union regions の連結新仕様

### 4.1 現行の問題

`_cell_text`（`mapping.py:108-127`）は欄に属する全 symbol を y でチェーンクラスタし、各行を x 順に並べるだけで領域の概念がない。左右に並ぶ領域（コの字）では左右の文字が1行に潰れて交互に混ざり、縦に接する領域（L 字）では筆跡次第で2行が融合する。

### 4.2 新しい連結順

```
regions = 採用した受け皿の並び
          通常は (rect, *extra_rects)、参照先採用時は (fallback_rect,)

1. 各 symbol を regions の定義順 first-hit で領域へ振り分ける
2. 領域を「帯」へまとめる:
     領域 A と B の y レンジの重なり高 >= 0.5 * min(A.h, B.h) なら同じ帯（推移的に併合）
3. 帯を y_min 昇順に並べ、帯の中の領域を x_min 昇順に並べる
4. 領域ごとに y のチェーンクラスタ（_LINE_GAP = 30px）で行に分け、各行を x 昇順に並べる
5. 帯順 → 領域順 → 行順 → x 順で連結する
   char_confs（§8.1）も同じ順序で作る。1 symbol につき len(symbol.text) 個の conf を並べる
```

「定義順で連結する」案は採らない。出荷テンプレの `person_住所1` は定義順が (主, 追加領域) だが、紙の読み順は追加領域（上段 y310）→主（下段 y368）で**逆**になる。定義順にすると住所が現行より悪化する。座標から帯を作る方式ならこの構成でも読み順が出る。

閾値 0.5 の根拠: 同じ帯に並ぶ左右の領域（コの字）は同じ行を表すので y レンジがほぼ全高で重なる。縦に積む構成は重ならないか、あっても罫線1本ぶん。出荷テンプレの実測は重なり **0px**（§1.2）なので、閾値をどこに置いても縦積みと判定される。0.5 は「半分以上重なっていれば同じ行帯」という素直な線。※コの字の実例は出荷テンプレに無いため、較正は合成ケース（§10 のテスト）で固定する。

### 4.3 既存テンプレで挙動が変わらないことの論証

1. **単一領域の欄（194欄中192欄）**: 手順1で全 symbol が唯一の領域に入り、手順2-3は自明。手順4は現行の `_cell_text` と同一のアルゴリズム。→ 出力は1文字も変わらない
2. **`person_住所1` / `person_住所2`（2領域）**: 主と追加領域の y レンジ重なりは0px（実測）なので手順2で別の帯になり、手順3で y_min 昇順＝追加領域(310) → 主(368)。正常な記入（上段の文字が下段の文字より上にある）では、現行の「全 symbol を y ソート」と同じ順序になる
3. **既存テスト `test_union_regions.py` の3件**: いずれも SPOT_A(y=1670) が主より下の縦積み。新方式でも帯は y 順に並ぶので期待値 `"前後"` 等は変わらない

異常時（上段の下寄り文字と下段の上寄り文字の y 差が 30px 未満になる筆跡）は**意図的に変わる**。現行は融合して文字単位で混ざり、新方式は領域の順序を保つ。これが #57 の修正そのもの。

## 5. U-07: 欄の穴（H-4 のコア側）

### 5.1 穴の定義

欄の受け皿群 `all_rects()` の外接矩形 `BBox` から、受け皿の和集合を引いた領域を**穴**と呼ぶ。単一領域の欄では BBox = rect なので穴は空。自動切り抜き（`carveField`）は必ず複数領域を作るため、切り抜きで開いた欠損は穴として表現される。

### 5.2 割付への組み込み

空間インデックス（`_bucket_cells`）に受け皿の**後ろ**へ穴を並べる。first-hit の順序が「欄の領域 → 参照先 → 穴」になるので、他の欄の受け皿に属する文字が穴に吸われることはない（穴として残るのは、定義上どの受け皿でもない場所だけ）。穴に落ちた文字は:

- その欄の `carve_hole` カウンタに加算する
- `unassigned_other` には**数えない**（穴は欄の内側であって枠外ではない）。この変更で `unassigned_other` はわずかに減るが、様式不一致 D-15 の判定は安全側（誤って様式不一致にする方向ではない）へ動く
- その欄を**欄全体〓**にする（判定表 #7）

部分〓（文字単位）にしない理由: 欠けたのは「どの文字か」ではなく「どこかの文字」で、位置が分からない。読めた文字だけを並べると部分値＝誤値になる。欄全体〓が正しい。

### 5.3 誤検知の実測

出荷テンプレで穴を持つのは `person_住所1`・`person_住所2` の2欄（面積比12%）。実応答でその穴に落ちた文字は住所1が8字・住所2が6字だが、**そのすべてが郵便番号の参照先に属する**ため、他の受け皿に属さない文字は 0字（§1.3）。正常ページでは1件も発火しない。発火するのは §3 の U-02 で参照先が無効になったとき——つまり本当に文字が行き場を失ったときだけ。

### 5.4 限界

## 8. 文字単位〓（#62）

### 8.1 U-10: 置換をどこでやるか

**置換は render 段（`render_rows.build_row`）で行う。`mapping._cell_text` では置換しない。**

理由は既存の不変条件「閾値の適用は render 段だけ。cell には読取値と信頼度しか入っていない」（`render_rows.py` の冒頭）を壊さないため。mapping で置換すると:
- 閾値を変えるたびに `remap` が必要になる（現在は `render` だけで反映される）
- 中間データに閾値の判断が焼き込まれ、同じ中間データから違う閾値の出力を作れなくなる

代わりに mapping は**事実だけ**を渡す。`CellContent` に `char_confs: tuple[float, ...]` を足し、`cell` テーブルへ `char_confs TEXT NOT NULL DEFAULT ''`（小数3桁のカンマ区切り・例 `0.977,0.312,0.964`）として保存する。順序は §4.2 の連結順と同一。

**不変条件**: `len(char_confs) == len(raw_text)`。1 symbol の text が2文字以上の場合は同じ conf をその文字数ぶん繰り返す。長さが一致しない、または `char_confs` が空（旧版が書いた中間データ）の場合は、文字単位〓を適用せず**欄全体〓へ倒す**（安全側）。旧データは `remap`（API 送信なし）で埋まる。

### 8.2 U-11: 適用範囲

| 対象 | 文字単位〓 | 理由 |
|---|---|---|
| 単純 text 欄（subfields 無し・normalize 無し）・出荷テンプレで145欄 | **適用する** | #62 の要望そのもの |
| subfields を持つ欄（10欄） | 適用しない | `split_composite` が〓混じりの文字列を分割できず結局失敗する。従来どおり欄全体〓 |
| normalize=amount（28欄） | 適用しない | PM スコープの Could（今回やらない）。金額に〓が混ざると数値型で書けない |
| choice（11欄） | 適用しない | PM スコープの Won't。候補照合の結果であって文字列の読み取りではなく、文字単位が成立しない |

閾値は**既存の `config.unclear_threshold` を共有する**。専用閾値は作らない——2つ持つと「欄の〓」と「文字の〓」で基準がずれ、QA が懸念した「〓の基準がバラつく」状態を自分で作ることになる。

最低信頼度列（管理2列目）は「出力された文字のうち〓に置換されなかった文字の最小値」とする。既存の B-1（出ていない値の信頼度を混ぜない）を文字単位へそのまま延長したもの。全文字が置換された欄は従来どおり母集団に入らない。

### 8.3 U-13: COUNTIF 互換（結論）

**現行の数式は完全一致で、そのままでは文字単位〓を数えられない**（§1.1）。`旭〓市` は `COUNTIF(範囲,"〓")` に当たらないため、〓が残っているのに要確認セル数が0になる。README の運用「合計が0になったら完成」は出荷ゲートそのものなので、これは**無言で嘘をつくゲート**になる。設計原則「失敗は無言にしない」に真正面から反する。

したがって3経路すべてを「〓を含む」へ揃える。

| 経路 | 変更前 | 変更後 |
|---|---|---|
| xlsx 管理列 | `=COUNTIF(G2:HL2,"〓")` | `=COUNTIF(G2:HL2,"*〓*")` |
| xlsx 条件付き書式（欄全体〓） | `CellIsRule(equal, '"〓"')` | 変更なし（既存の色 `FFF2CC` を維持） |
| xlsx 条件付き書式（一部〓） | — | `FormulaRule(['AND(ISNUMBER(FIND("〓",G1)),LEN(G1)>1)'])` ＋ 淡い橙 `FFE8CC` |
| csv 静的値 | `v == "〓"` | `isinstance(v, str) and "〓" in v` |

互換性の評価:

1. **我々が出力する集計は壊れない**。文字単位〓が OFF のとき、〓は必ず単独のセル値なので `"*〓*"` と `"〓"` の結果は一致する。ON のときは「人が見るべきセルの数」という列の意味が保たれる（欄全体でも一部でも、オペレーターが直すのは1セル）
2. **xlsx と csv の一致（§8-12）も保たれる**。両方を同じ「含む」の定義に変えるため
3. **利用者が別途組んだ完全一致の集計は、機能を ON にしたときだけ過少カウントになる**。これは避けられない意味の変更なので、①既定 OFF ②README とリリースノートに明記 ③ON 後の1バッチを実データで確認してから既定を反転、の段階導入で扱う
4. 2つの条件付き書式は式の上で排他（一方は完全一致、他方は「含む かつ 長さ2以上」）なので、優先順位や `stopIfTrue` に依存しない
5. 金額列（数値型）に対して `COUNTIF(...,"*〓*")` のワイルドカードは当たらず、`FIND` は `#VALUE!` → `ISNUMBER` が FALSE になるため書式も付かない。どちらも安全側

**未確認事項（実装前に必ず潰す）**: openpyxl は数式を評価しないため、`COUNTIF(範囲,"*〓*")` が Excel 実機で期待どおり数えることは自動テストで確認できない。§10 のテスト T-16 として**実機1回の確認（コマンド・値・実行日を証跡として残す）**を受け入れ条件に置く。ここで想定と違った場合に限り、#62 を切り離して残り（#54/#57/H-4/H-6）で進める。

**QA 再判定（2026-08-31・T-16 ブロッカーの解消）**: T-16 未検証のまま出荷すると、既定 OFF（大半の利用者）の経路にも未検証のワイルドカード仮定が乗ることが実装後に判明した。そのため3経路の「含む」化は `unclear_char_level` でゲートする——OFF では COUNTIF・条件付き書式（1本のみ）・csv 判定のすべてが本節の「変更前」の完全一致に戻り、ON にしたときだけ「変更後」が有効になる。T-16 の実機確認は「#62 全体の受け入れ条件」から「ON へ既定反転する前の受け入れ条件」へ位置づけを移した（§8.5 も参照）。

**T-16 実機確認（2026-09-01・確認済み）**: `unclear_char_level=True` で `render_rows.build_row` → `render_out.write_outputs` を通し（API 送信なし・コア変更なし）、Excel 16.0 の COM 経由で実機を開いて `COUNTIF(範囲,"*〓*")` の計算値を読み取った。想定どおりの挙動であることを確認し、#62 を切り離す判断は不要になった。

- 実行コマンド: `.venv\Scripts\python.exe -X utf8 t16_gen.py`（xlsx/csv 生成）→ `powershell -NoProfile -ExecutionPolicy Bypass -File t16_verify.ps1`（`New-Object -ComObject Excel.Application` で `Visible=$false`・`DisplayAlerts=$false` で開き、`.Value2`（計算結果）を取得後 `Quit`＋COM 解放）

### 8.4 U-12: 「欄全体〓」と「一部〓」の区別（要決定への回答）

**決定: 記号は `〓` 1種類のままとし、区別は「セル値の形」で表す。**

- **欄全体〓** = セル値がちょうど `"〓"`（長さ1・完全一致）
- **一部〓** = `"〓"` を含み、かつ長さ2以上

これを成立させるための不変条件を置く: **全文字が閾値未満の欄は `"〓〓〓"` のような全〓文字列を作らず、必ず1文字の `"〓"` へ畳む**（判定表 #11）。畳まないと「完全一致＝欄全体〓」が崩れ、区別の土台が壊れる。

| 用途 | 区別の方法 |
|---|---|
| 集計（我々が出す列） | 「要確認セル数」は両方を1件として数える。列の意味は「人が見るべきセルの数」であって〓の粒度ではないため |
| 集計（利用者が知りたいとき） | `COUNTIF(範囲,"〓")` が欄全体〓の数、`COUNTIF(範囲,"*〓*")` との差が一部〓の数。上の不変条件があるので**この2式は常に正しい**。README に1行で書く |
| 目視 | 条件付き書式を2つに分ける。欄全体〓＝既存の `FFF2CC`（見た目を変えない＝既存運用が変わらない）／一部〓＝淡い橙 `FFE8CC`。橙は debug-images で「信頼度不足」を表す色と系統が揃う |

**この決定の根拠**:
1. 新しい記号（例: `▲`）を導入すると、既存の集計・条件付き書式・README・オペレーターの記憶がすべて二重定義になる。QA が最も警戒している「〓の基準がバラつく」状態を仕様として作ってしまう
2. 色だけで区別すると csv では区別できない。値の形で区別すれば csv でも同じ判定ができる（`== "〓"` か `"〓" in v` か）。xlsx と csv で意味が一致する
3. 作業内容が違う（欄全体＝全部入力し直す／一部＝1文字直す）ので、色は分けるだけの価値がある。色は補助であり、値の形が正
4. 「見た目のカスタマイズ」（利用者が色を選べる機能）は Won't のまま。固定色を1つ増やすのは仕様であってカスタマイズではない

### 8.5 U-14: 設定と段階導入

- **GUI の設定画面には出さない**（要件 §5.8「設定6項目」を増やさない。`api_monthly_cap` と同じ扱い）

## 10. データ構造の変更とマイグレーション

### 10.1 `cell` テーブル

```sql
ALTER TABLE cell ADD COLUMN char_confs TEXT NOT NULL DEFAULT '';
ALTER TABLE cell ADD COLUMN origin     TEXT NOT NULL DEFAULT '';
```

`store.py` の `_ensure_column` に2行足すだけ（既存 DB へも適用される既存の仕組み）。既定 `''` は「旧版が書いた・情報を持たない」印で、`char_confs=''` なら文字単位〓は適用せず欄全体〓、`origin=''` なら由来印なし。`remap` で埋まる（API 送信なし）。

### 10.2 呼び出し側の後方互換

`store.cells()` の戻り値（4要素タプル）は**変えない**。拡張分は新メソッド `store.cell_extras(page_id) -> dict[str, tuple[str, str]]`（`char_confs`, `origin`）として足し、`build_row(template, page, cells, era_scores, cfg, extras=None)` の**既定 None で従来挙動**にする。

理由: `store.cells()` の戻り型を変えると `render`・`debug_images`・既存テスト（`test_render_rows.py` は cells 辞書を手で組む）が一斉に壊れる。回帰要件「既存テストが緑のまま」を型で守る。

**不変条件**: 同一 `page_id` に対し `cells()` と `cell_extras()` のキー集合は一致する。

### 10.3 `page` テーブル

`unassigned_other` はそのまま。新しい件数（`fallback_discarded`・`carve_hole`）は page 単位のカウンタとして持つか、run 単位の集計だけにするかを実装時に選ぶ。**設計上の要件は「ページ単位で件数が分かり、進捗イベントと run サマリに出ること」**で、置き場所は自由。列を足す場合は 10.1 と同じ `_ensure_column` パターン。

## 14. 守るべき不変条件

1. セル値が `"〓"` と完全一致 ⇔ その欄は全体が要確認。`"〓"` を含み長さ2以上 ⇔ 一部の文字が要確認。**全〓文字列（`"〓〓"` 等）を作らない**
2. `len(char_confs) == len(raw_text)`。一致しない・空のときは文字単位〓を適用せず欄全体〓へ倒す
3. 閾値の適用は render 段だけ。中間データに閾値の判断を焼き込まない
4. 値そのものを書き換えない（転記主義）。〓は「値を出さない」ことの表現であって、値の加工ではない
5. xlsx と csv で「要確認セル数」の値が一致する（§8-12）
6. 参照先は「主が空のときだけ有効な受け皿」。無効なとき参照先の文字は消えてはならず、必ず穴・枠外のどちらかに分類される
7. 割付の first-hit 順序は「欄の領域（定義順）→ 参照先 → 穴」。穴が他の欄の受け皿より先に文字を取ることはない
8. 出力列数はこの設計で1つも増減しない（220のまま）
   - ※限定（2026-09-01・issue #66）: **[05_output_columns_requirements.md](05_output_columns_requirements.md)（出力列制御）の `output` による列の減少と、並べ替えによる列順の変化は本条の対象外**。本条が縛るのは〓の統一設計（U-01〜U-15）が列を増減させないことであって、列構成を意図的に変える機能まで禁じるものではない。列が可変になった後の決定性は 05 §5 NFR-04 が別途担保する
9. 同一中間データ・同一設定からの出力はバイト一致する
