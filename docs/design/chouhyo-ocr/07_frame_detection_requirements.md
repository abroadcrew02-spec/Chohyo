**v0.3 で構造が変わった点**

1. **(a) を「新スコアの新設」から「既存判定の接続」へ縮めた**（critic Must-1・architect M-6）。関係のない紙は**既に送信前に止まっている**——`estimate_shift` が `ok=False` を返し、`align_page` が `AlignError` を投げ、`pipeline.py:513-521` が `status=位置合わせ失敗` を立てて Vision 送信前に `continue` する。v0.2 の「送信前に止める」という期待効果は**既存ゲートを勘定に入れていない誤り**だった。増分価値は §1.3 の4点（枠を描かないこと／結果を記録すること／ステータスと理由コードを分けること／判定をテンプレート選択に使えるようにすること）に縮む
2. **判定を2値から3値へ**（一致／不一致／判定不能。critic S-5・architect M-7）。`aligned:false` には「正しい様式だが罫線がかすれた紙」が含まれ、2値で枠を消すとこの紙で枠が消える
3. **テンプレートの保存・選択・照合提示を In へ引き上げた**（ユーザーの目標フロー＋critic Must-4）。v0.2 は「新テンプレートを作れるが GUI から読み取れない」という中間状態を作っていた
4. **枠候補に「単発欄候補」を追加**（architect M-8・designer M-4）。`detect_ruled` は `if len(h_lines) < 3: return None` で単発の1マス枠を必ず落とすため、欄候補の生産経路が現行に無い
5. **吸着の許容幅を軸別へ**（qa_lead M-1・architect M-1）。`min(行間隙, 列間隙)` は現存全テンプレートで **0px**（列が接しているため）になり、fail-safe が常時発動して吸着が永久に no-op になる。この状態でこそ v0.2 の AC-F09 は確実に通る（緑偽装）
6. **「倍率差 0.3% で面の端が約 7px」の記述を撤去**（architect M-5・ルール2）。この数値は設計書の実測ではなく Orchestrator が会話中に出した算術推定（0.003 × 2490 ≒ 7.5px）だった。02 D-25 から引けるのは「detail の行間隙 4px で ±2px からラベル混入・±12px で元号誤選択・スケールは補正しない」のみ

### 0.2 v0.4 で構造が変わった点（2周目レビュー）

1. **`few_lines` を検出線の本数で二分した**（critic 2周目 Must-A）。**v0.3 は中核要望と正面から矛盾していた**——無関係な A4 縦の紙は期待線との一致が下限未満となり `few_lines` に落ちる（他3コードは下限を通過した後にしか到達しない・`align.py:117-120`）。v0.3 の対応表は `few_lines` = 判定不能 = 枠を描く なので、「関係ない PDF を開くと枠が描かれる」ままだった。しかも AC-F02 の素材（同寸の別様式）が未作成のため、テストでも当面露見しない。`estimate_shift` は検出線 `det_h`／`det_v` を下限判定の**前**に計算済み（`align.py:96-110`）なので、その本数を返すだけで二分できる（新しい画像処理はゼロ）。※v1.2 で**軸別判定**へ精緻化し、あわせて `edge_mismatch` の分類を訂正した（§0.7）
2. **テンプレートの保存先を `templates/` から `templates_user/` へ変えた**（critic 2周目 Must-B・Orchestrator 判断）。`gui/src-tauri/tauri.conf.json:39` の `"../../templates": "templates"` により `templates/` はディレクトリごと配布物へ同梱される。v0.3 のままでは利用者の顧客固有テンプレートが次のビルドで配布物へ混入し、インストール環境ではアプリ更新で置き換えられうる場所へ利用者データを書くことになる
3. **吸着を y 軸のみに絞った**（critic 2周目 Must-F・Orchestrator 判断）。列間隙は全テンプレートで 0 であり、「列間隙 0 ＝ x へ 1px でも隣列に食い込む」を厳密に適用すれば x 軸の安全な吸着量は 0。v0.3 の x 軸許容幅（最小列幅に対する割合）は「機能させたい」という都合が根拠になっていた。**x 軸は仕様として no-op** とし、Q-03 受領後へ送る。⚠️ ユーザー判断 Q-F4=B の期待値に触る変更のため、Orchestrator からユーザーへ報告する
4. **部分 fail-safe を禁止した**（critic 2周目 Must-E・Orchestrator 判断）。同じ面に吸着したブロックと戻したブロックが混在する状態は、§3.3 の「片面失敗でページ全体を失敗」および D-25 の「半分だけ正しい状態を正常顔で出さない」と矛盾する。**1ブロックでも fail-safe に落ちたら、その面の全ブロックをテンプレート座標へ戻す**
5. **ON/OFF 差分一覧を診断コマンドとして定義した**（critic 2周目 Must-D・Orchestrator 判断）。v0.3 は実行条件を書いておらず、素直に読むと `run` を2回回す＝**課金2倍**になりうる。保存済み中間データに対して割付を再計算する形にし、Vision 送信ゼロを AC で縛る
6. **実施順序を (a') → (t) → (b) → (c) → (f) へ変えた**（critic 2周目 S-2）。既存の2テンプレート（`templates/chouhyo-v1.json`・`testdata/formB/formB-v1.json`）だけで (t) の全 AC が回り、**既存様式を使い分ける利用者には (b) の完成を待たずに価値が出る**

### 0.3 v0.5 で塞いだ穴（3周目 architect）

v0.4 は「1ブロックでも fail-safe に落ちたら面全体を戻す」（FR-F42）と決めたのに、**部分適用が成立する経路が2つ残っていた**。

1. **AC-F34 が v0.3 のまま残置されていた**（M-1）。「同じ面の他ブロックの吸着は妨げられない」という一文が FR-F42 と正面から矛盾し、テストが部分適用を要求する状態になっていた
2. **小さい表の除外（FR-F35）が FR-F42 のどちら側か未定義だった**（M-2）。除外ブロックと吸着ブロックが同じ面に共存すると、**fail-safe を経由せずに部分適用が成立する**。除外は fail-safe の判定より手前にあるため、FR-F42 の網に掛からない

いずれも「面スコープで揃える」側に倒した。加えて、除外が**テンプレート保存時に予見できる**こと（表の行数はテンプレートに書いてある）を利用し、`verify` の警告として作成者へ先に伝える要件を足した（FR-F48）。

### 0.4 v0.6 で締めた (t) の権限拡大（3周目 security）

(t) は「ディレクトリ列挙」と「一括読み取り」という新しい権限を要求する。v0.5 の書き方はその境界が緩かった。

1. **名前検証を拒否リストから許可リストへ**（M-1）。「パス区切りと `..` を拒否」では Windows 予約デバイス名・末尾ドット／空白・`:`（代替データストリーム）・制御文字が通る
2. **シンボリックリンク／ジャンクションの再検査を全操作へ**（M-2）。#69 S-N3 で同型の穴を塞いだ前例がある——`lib.rs:386-395` は canonicalize の**結果にも** `is_safe_root` を通しており、生パスだけの判定ではジャンクション1本で範囲がドライブ全域へ広がる
3. **列挙対象を `templates_user/` のみに縮めた**（Q-S3）。出荷テンプレートは「固定1件の既定候補」として照合に加え、**列挙はしない**。権限拡大が片側で済む
4. **既定テンプレートの永続に絶対パスを保存しない**（M-3）。ディレクトリ区分＋ファイル名で持ち、読み出し時に範囲を再検査して外れていれば出荷テンプレートへフォールバックする。前例は `workdir_pages_dir`（`lib.rs:356-369`・読み取り時に `is_safe_root` を再実行）
5. **`config.json` の新キーは3箇所同時更新**（M-7）。Rust の `KNOWN_CONFIG_KEYS`（`lib.rs:797-802`）と Python の `Config` dataclass・`_validate` のいずれかが欠けると、**設定ファイル1つで全コマンドが起動不能**になる（`lib.rs:808-811` のローカル DoS 注記）
6. **配布物・git への混入防止を要件化**（M-6）。`templates_user/*.json` は現状 `.gitignore:51` の `*.json`（全階層）の副作用で偶然無視されているだけで、明示行が無い

### 0.5 v1.0 で確定した3点（3周目 critic・qa_lead）

1. **吸着の検証素材を片ブロックのみの平行移動に確定した**（critic Must-2・qa_lead M3-1／M3-2）。両面とも2ブロックは x 方向に並んで **y スパンを共有する**（front/family 907..1472・back/detail 93..1549）ため、**等比拡大では y 補正がブロック間で同一になり D-25 が吸収してしまう**——v0.5 の AC-F30b・AC-F31（等比拡大型）では ON/OFF に差が出ない。⚠️ このとき机上で導いた「成立窓は δ=3 の1点」は **v1.2 で実測により δ=2〜5 へ訂正した**（§0.7 訂正2）

### 0.7 v1.2 の訂正（実測に基づく・2026-09-02）

前提作業 §10.2-1／-2 の実測（commit `37d6e5f`・`testdata/formC/README.md`・`core/tests/helpers_geom.py`）で、**机上で決めていた2点が事実と食い違っていた**。

**訂正1: `edge_mismatch` は「不一致」ではなく「判定不能」**

v1.1 は `edge_mismatch` を不一致（＝枠を描かない）に置いていた。実測はこれを否定する——**本物の紙（`sample-1`）の `back/detail` の水平罫線を上から1本白塗りしただけで `edge_mismatch` に転じる**（matched 36/42・実行日 2026-09-02）。上端行が消えると他の行がすべて健在でも即座に発火する。外形アンカー検査（02 D-25 手順6 ④）が `few_lines` の 50% 閾値よりはるかに敏感なため。

不一致のまま置くと **§9.1 が避けたかった「本物の紙で枠が消える」がまさに起きる**。判定不能へ移して枠を描く現行挙動を維持する。

**中核要望は損なわれない**——同寸の別様式（合成 `formC-1.png`・2490×3510）を出荷テンプレートに通すと **両面とも `few_lines`**（front 2/22・back 7/42）で落ちる。`edge_mismatch` は「無関係な紙」の経路ではなく「正しい様式が部分的に劣化した入力」の経路だと実測で分かった。

| 入力 | 実測の理由コード | v1.2 の3値 | 枠 |
|---|---|---|---|
| 無関係な別様式（formC・同寸） | 両面 `few_lines`（検出線は十分） | 不一致 | **描かない** ← 中核要望 |
| 本物だが上端1本かすれ | `edge_mismatch` | **判定不能** | 描く ← v1.2 で訂正 |
| 本物だが上端 12 本以上かすれ | `few_lines`（検出線が乏しい） | 判定不能 | 描く |

**訂正2: 吸着刺激の δ 窓は「δ=3 の1点」ではなく δ=2〜5**

v1.0 は `SHIFT_RUNNER_DIST = 4`・`SHIFT_GAP_MIN = 2` から「成立窓は `2 < δ < 4`＝δ=3 のみ」と推論していた。実測（`back/detail` の block1 のみ y 方向 δ px・δ=0..9 の1刻み掃引）は **δ=2〜5 で成立**（面の `dy` は 1 に収束し、block1 の残差は δ−1）、**境界は δ=5（ok）→ δ=6（`ambiguous`）**。机上の推論が窓を1点に狭めすぎていた。

刺激は **δ=4（block1 の残差 3px）** に確定する——許容幅 4px の内側で最大の残差が得られ、境界（δ=6）から2つ離れているため。

### 0.8 v1.3 の変更（Step 2 (t) の設計反映・2026-09-02）

## 1. 概要 / 背景

### 1.1 利用者が困っていること

利用者が関係のない PDF を編集画面で開くと、出荷テンプレート `templates/chouhyo-v1.json` の枠がそのまま画像へ重なって表示される。枠は入力画像から検出したものではなく、テンプレート座標を描いているだけなので、**紙が違っても枠は同じ位置に出る**。

**「枠がそのまま出続けること」が、利用者に「枠判定がされていない」と感じさせた決定的な要因**である（2026-09-02・ユーザー回答）。案内文の有無ではない——現行も `aligned:false` の案内は表示されている。したがって本件の中核は「不一致のときに枠を描かないこと」であり、これを Must で確定する。

**投入されたのは「今後扱いたい別様式」ではなく無関係な書類だった**（2026-09-02・ユーザー回答 Q-F18）。したがって本件の中核は **(a') の「不一致なら枠を描かない」**で確定する。保存済みテンプレートの照合提示 (t) は、この要望に直接応えるものではなく**副次的な価値**（目標フロー §3.1 の「テンプレ保存してるなら読込」に対応し、複数様式を使い分ける運用を成立させる）と位置づける。

もう1つの痛点は作成コスト。**枠を引く手間と、名前・種別を付ける手間が同じくらい重い**（2026-09-02・ユーザー回答）。現行の作成支援は「人が外枠と行数・列数を指定する等分割生成」と「人が囲った領域内の罫線検出」の2つで、どちらも人が先に領域を指定する。`detect-grid` は CLI 引数 `--region` が必須（`core/chouhyo_ocr/cli.py:572`）で、ページ全体から枠を洗い出す経路が無い。

### 1.2 現状の判定ゲートの実際（v0.2 の誤りの訂正）

v0.2 は「関係のない紙は送信＝課金の後に全〓行になる」と書いたが、これは**誤り**。現行のゲートは3つあり、順に効く。

| # | ゲート | 判定時点 | 何を止めるか |
|---|---|---|---|
| 1 | `page_size_verdict`（`align.py:270-292`） | 送信前 | 縦横比の相対差 1% 超。用紙違い（実測差 約8%）・向き違い（約41%）。**同じ A4 縦の別帳票は通る** |
| 2 | `estimate_shift`（`align.py:114-138`） | **送信前** | 罫線の一致本数が下限（`SHIFT_MATCH_RATIO = 0.5`）未満、探索境界、次点との差不足、上端下端の不一致。`AlignError` → `pipeline.py:513-521` が `status=位置合わせ失敗` を立てて `continue` |
| 3 | D-15 枠外トークン率 0.55 | 割付後（**送信後**） | 様式違い。位置ズレは検出しない（02 §6.2 実測: ±18px で 177/212 崩壊しても不発火） |

**無関係な A4 縦の紙は、実際にはゲート2でほぼ確実に落ちる。** 課金も発生していない。ゲート3だけを見て「送信後にしか判定できない」と書いたのが v0.2 の誤りだった。

### 1.3 本件の増分価値

ゲート2は既に「一致本数 `matched` / 期待本数 `total`」と失敗理由（4種）を計算して保持している。**足りないのは判定そのものではなく、その結果の使い道**である。

1. **編集画面がその結果を使っていない**——`aligned:false` でも枠を描き続ける（利用者が「判定されていない」と感じた原因）
2. **結果が捨てられている**——`matched/total` と理由は画面にもログにも残らず、較正の母集団が貯まらない
3. **ステータスが混ざっている**——様式が違う紙も、罫線がかすれた本物も、同じ `位置合わせ失敗` に入る
4. **判定結果をテンプレートの選択に使えない**——GUI の読み取りは `lib.rs:147-149` が常に `templates/chouhyo-v1.json` を注入し、`RunScreen.tsx` にテンプレート選択が無い

本件はこの4点を埋める。**新しい画像処理は (b) の枠候補生成だけ**で、様式判定は既存計算の再分類にする。

## 3. 業務要件

### 3.1 目標フロー（2026-09-02・ユーザー提示。最上位の制約）

> 画像を読み込む → 自動で枠判定 → テンプレ保存してるなら読込 or 手動で調整、保存 → OCR 実行

入口が**画像起点**である点が現行と逆になる。現行の編集画面は起動時に出荷テンプレートを自動読込し（`Editor.tsx` のマウント時処理）、その後に画像を開く。本件はこの順序を要件として組み替える。

| フローの段 | 対応する要件 |
|---|---|
| 画像を読み込む | 画像を先に開ける（テンプレート未選択でも作業を始められる）・FR-F06 |
| 自動で枠判定 | (b) ページ全体からの枠候補生成・FR-F13〜FR-F24 |
| テンプレ保存してるなら読込 | (t) 保存済みテンプレートの照合提示・FR-F27（**確定は人**。確認なしの自動選択は後段） |
| 手動で調整、保存 | 候補の採用・命名・保存・FR-F19〜FR-F25 |
| OCR 実行 | 実行画面でそのテンプレートを選んで run・FR-F26 |

### 3.2 本件で読み取り結果が変わる範囲

吸着 (f) が In にあるため（Q-F4=B）、本件の成果物は既存の読み取り出力を変えうる。回帰の切り分け手段を要件として明文化する。

1. **吸着は既定 OFF**（Q-F7=OFF・critic S-1・qa_lead）。許容幅**内**の誤吸着を検出する下流が存在しない（§3.5）以上、実データで較正するまで既定 ON にすると配置誤りが正常顔で出る
2. **ON/OFF を設定で切り替えられ、中間データに記録して再利用時に照合する**（FR-F37・FR-F38）。ON で `run` → OFF に書き換えて `remap` という素通りを塞ぐ
3. **`ALGO_VERSION` を `"2"` → `"3"` へ上げ、旧方式の中間データを再利用しない**（FR-F42・D-26）
4. **吸着 ON/OFF の読取値差分をセル単位で記録し、一覧できる**（FR-F39・critic 示唆3）

### 3.3 吸着を入れても変えないもの

- 枠の**個数と対応関係**。吸着は既にテンプレートに定義された枠の位置を動かすだけで、枠を増やしも減らしもしない（01 §8）
- 面ごと独立に補正する原則と、片面失敗でページ全体を失敗にする扱い（01 §5.2・02 §6.2）
- **枠座標の不変条件の扱いは要件で決める**（architect M-2）。現行 D-25 は画像を動かして枠座標を据え置くため、`remap` の `assign(template.cells, ...)` と `era.score_cell(binary, cell)` がテンプレ矩形をそのまま使える。ブロックごとに違う量を動かすとこの不変条件が崩れる。本件は FR-F36 で「吸着後座標を `alignment.transform` へ永続化し、`remap`・`render`・元号再スコアが同じ座標を復元する」側を採る（`alignment.transform` は JSON 列で入れ物は足りる——`store.py:55-58`）

### 3.4 実施順序と依存関係（**確定**・2026-09-02）

```
(a') 既存判定の接続（3値化・理由コード分離・スコアと理由の記録）
       ↓  同じ判定関数をテンプレート単位で呼べる形にする
(t)  テンプレートの保存・選択・照合提示
       ↓  新しい様式を作る手段を足す
(b)  ページ全体からの枠候補生成
       ↓  吸着量を記録する土台を先に置く
(c)  位置合わせ残差・吸着量の記録
       ↓
(f)  実行時のブロック単位吸着（最後段・既定 OFF・y 軸のみ）
```

**順序はユーザーの委任（Q-F5「指定なし・おまかせ」・2026-09-02）を受けて本書の判断で確定した。期限は設けない。**

- **(a') が最初**: **本件の中核**（Q-F18）であり、新しい画像処理を伴わない。加えて (t) の照合と (b) の入口判定の両方が同じ判定関数に乗るため、ここが決まらないと後続の入力仕様が決まらない
- **(t) の着手条件**: ~~§10.2-8（Q-F16）~~ → **v1.3 で解消**。保存先を `app_data_dir()` へ移したことで更新耐性・ACL・配布物混入が構造で成立し、実測待ちが無くなった（§0.8 変更1）。**(t) は着手可**
- **(t) は中核ではないが (b) より先のまま**（Q-F18 の回答後も順序を変えない）。理由は2つ——①**既存の2テンプレートだけで (t) の全 AC が回る**ので、(b) の完成を待たずに検証できる ②目標フロー §3.1 の「テンプレ保存してるなら読込」が (t) に当たり、これが無いと (a') で不一致になった紙の行き先が無い。中核ではないことは §4.1 (t) に明記した
- **(t) が (b) より先**（v0.4 で入れ替え）: 既存の2テンプレート（`templates/chouhyo-v1.json`・`testdata/formB/formB-v1.json`）だけで (t) の全 AC が回るため、**(b) の完成を待たずに検証できる**。かつ「複数の既存様式を使い分けたい」利用者には (b) 無しで価値が出る——新しい様式を作る必要が無く、選べないことだけが障害だった層
- **(b) は (t) の後**: 「不一致だった紙で新しいテンプレートを作る」導線の中身が (b) なので、導線が空振りする期間を作らないよう (a') の導線部分は (b) の完成を待って有効化する。保存・選択の受け皿（(t)）が先にある方が、作ったテンプレートの行き先が最初から存在する
- **(f) は最後段**: (c) の記録が無いと吸着が効いたのか暴れたのかを事後判定できない。かつ本件で唯一 読み取り出力を変えるため、他が全部緑になってから入れる
- **(f) と (b) は検出処理を共有しない**（architect 問い4 の指摘を採用）。(b) はページ全体・領域未知、(f) は面内・領域既知で、共有できるのは `line_positions` までと見る。v0.2 の「検出処理を共有する」は撤回
- **(f) の着手条件**: §10.2-2（AC-F30 用の変形素材と、画像・応答へ同じ変換を掛ける2関数）の完了をもって着手可とする。素材が無いと効果を測れないため
- **(f) の完了定義**: 「**既定 OFF で実装が完了し、L2 で ON 側の AC（AC-F30〜AC-F43）が合成素材で全緑**」をもって完了とする。**「既定を ON に反転する」ことは完了条件に含めない**——それは Q-F14（実データ受領後・差分一覧の確認者と受け入れ基準）で別途判断する

### 3.5 (f) の残存リスク（critic Must-5・要件として明記する）

**許容幅の内側で誤った方向に吸着した場合、それを検出する下流が存在しない。** 02 §6.2 の実測どおり D-15 は位置ズレを検出せず（±18px で 177/212 崩壊しても不発火）、`status=正常` のまま配置が壊れる。§3.2 の4点は**事後の切り分け手段**であって、誤りに**気づく**手段ではない。

本件はこのリスクを消せない。緩和として次の3つを要件に置く: ①既定 OFF（FR-F39）②「信用する下限」を設けて期待横線 4 本以下のブロックを含む面を吸着対象外にする（FR-F35）③ON/OFF の読取値差分を人が一覧できる（FR-F40）。**それでも残るリスクは Q-F11 として未解決に置く。**

さらに **効果の帯そのものが極めて狭い**（qa_lead 2周目 問い1・critic 3周目 S-3）。detail で見ると、害が出始めるのは ±2px から（02 D-25 実測のラベル混入）、許容幅の上限は行間隙 4px。**救う価値がある帯は 2〜4px＝幅 2px しかない。** さらに FR-F42 により片ブロックでも fail-safe に落ちれば面全体が吸着しないため、実際に効く場面はこれより狭い。**その帯の中の誤りに気づく手段が無い**——既定を ON にするかどうかの判断材料として Q-F14 に引き継ぐ。

### 4.1 In Scope

#### (a') 既存判定の接続・3値化・理由コードの分離 ★**本件の中核**（Q-F18 で確定）

- `estimate_shift` が既に計算している `matched / total` と失敗理由を、**判定関数として切り出して画面と記録へ流す**。新しい画像処理は足さない（critic 示唆1・architect M-6）
- 判定は**3値**（一致／不一致／判定不能）。既存の4つの失敗理由を次の対応表で分類する（FR-F02）。**`few_lines` だけは検出線の本数で二分する**（FR-F45・§0.2-1）——`estimate_shift` は検出線 `det_h`／`det_v` を下限判定の前に計算済み（`align.py:96-110`）なので、その本数を返すだけで足りる。新しい画像処理は伴わない（§9.1 の制約内）

| `estimate_shift` の reason | 意味（`align.py:114-138`） | 本件の3値 | 根拠 |
|---|---|---|---|
| （`ok=True`） | 一致本数が下限以上・境界外・次点と差あり・端一致 | **一致** | — |
| `few_lines` かつ **検出線が乏しい** | 最良シフトでの一致本数 < `max(2, ceil(期待線×0.5))`、かつ検出線の本数が期待線本数の 50% 未満 | **判定不能** | **線が取れていない**（汚れ・かすれ・二値化の失敗）。断定せず現行動作（枠を出す）を維持する |
| `few_lines` かつ **検出線は十分** | 最良シフトでの一致本数が下限未満だが、検出線の本数は期待線本数の 50% 以上 | **不一致** | **線は取れているのに期待位置と合わない＝別の紙。** ⚠️ `few_lines` は「検出線が少ない」ではなく「**一致本数**が少ない」条件（`align.py:117-120`）なので、無関係な紙は罫線が豊富でもここへ落ちる。これが「関係のない A4 縦の PDF」の落ちどころで、二分しないと枠が描かれ続ける（§0.2-1） |
| `boundary` | 最良シフトが探索境界にある | **判定不能** | 探索上限はテンプレの行ピッチ・列間隔から導出した値。境界に張り付いたということは**探索範囲の外に正解があるかもしれない**状態で、結論が出ていない。不一致と断ずると、大きくズレただけの正しい紙で枠が消える |
| `ambiguous` | 次点（4px 以上離れた位置）とのスコア差 < 2 | **不一致** | 複数の位置が同程度に合う＝この様式の周期構造と噛み合っていない |
| `edge_mismatch` | 各テーブルの上端・下端の横罫線が ±2px で一致しない | **判定不能** | ⚠️ v1.1 まで「不一致」に置いていたが**実測で訂正**（§0.7 訂正1）——本物の紙の上端罫線を**1本白塗りしただけで発火する**（`sample-1`・matched 36/42・2026-09-02）。外形アンカー検査（02 D-25 手順6 ④）は `few_lines` の 50% 閾値よりはるかに敏感で、「別の紙」ではなく「本物の部分的な劣化」を捕まえている。不一致に置くと §9.1 が避けたかった「本物で枠が消える」が起きる |
| `size`（`page_size_verdict` が `estimate_shift` の手前で `PageSizeMismatch` を投げる） | 縦横比の相対差 1% 超 | **不一致** | 判定の入口で落ちるため `estimate_shift` の理由コードは存在しない。**FR-F28 の N 件ループでは、画像サイズの違うテンプレートが必ずここに落ちる**ので対応表に明示が要る。単一テンプレートの編集画面では現行の `size` 案内（赤帯）を維持する（優先順は FR-F07） |

- **`few_lines` を二分する閾値**: **軸ごとに**、検出線の本数がその軸の**重複排除した期待線の位置数**の **50% 以上**なら「その軸は検出線が十分」とする（合算しない理由は FR-F45）。暫定値であり Q-F6 の較正対象（一致率の下限 `SHIFT_MATCH_RATIO = 0.5` とは別の量——前者は「線が見えているか」、後者は「見えた線が期待位置と合うか」）
- **分母を重複排除にする理由**（3周目 critic Must-1／qa_lead M3-5 を検算のうえ一部訂正して採用）: `det_h`／`det_v` は集合で、同じ位置に重なる期待線（front/family と back/detail はどちらも2ブロックが同じ y スパンを共有する）は1本に潰れる。検出本数を連結長（front 22・back 42）と比べると、完全な紙でも構造的に届かない。重複排除値は **front 16・back 26・formB 10**
  - ⚠️ **レビューが挙げた「完璧な紙でも 64%（back）・73%（front）にしか届かず 50% 閾値のマージンが 6 本しかない」という根拠は、検算の結果**成立しなかった**。`_axis_shift` のスコアは**連結リスト `expected` を反復して集合 `det` への membership を見る**（`align.py:69-71`）ため、同位置の重複した期待線は**それぞれ加点される**。実測: 完全な紙で front 22/22・back 42/42 = **いずれも 100%**、back の h 軸は 15 本中 8 本を失って初めて下限を割る（実行日 2026-09-02・`_axis_shift` に期待線の連結リストと重複排除した検出集合を与えて算出）。**したがって既存の判定（`matched/total`）は変更しない**——変更すると読み取り出力が変わり NFR-F08 と矛盾する
  - 重複排除を使うのは **①FR-F45 の二分（検出集合との比較なので分母も集合基準でなければ意味を成さない）②FR-F01／FR-F13 のテンプレート間比較スコア（ブロック数の違うテンプレート同士で桁を揃えるため）** の2つに限る。判定そのものは既存のまま
- ⚠️ **残存リスク: 中程度のかすれで本物が不一致に落ちる**（実測・2026-09-02）。`back/detail` の水平罫線を上から N 本白塗りした劣化列で、**N=8〜11 は `few_lines` かつ h 軸の検出線が下限（15×50%＝8本）以上**のため「不一致」＝枠が消える。N=12 以上は検出線が 7 本以下になり判定不能へ移る。つまり**劣化の途中に、本物なのに枠が消える帯がある**。受け皿は FR-F05（編集画面の上書き）と FR-F10（実行画面の出口2択）で、これは Q-F6 の較正対象として §10.3 に残す
- **判定が保証する範囲と保証しない範囲**（critic Must-2・architect M-10）:
  - 保証する: **罫線幾何の一致**のみ。テンプレートのテーブル定義から導いた期待罫線と、入力画像の検出線が同じ位置にあるか
  - 保証しない: 中身の同一性。**幾何が同じで印字内容が違う紙（同じ表組みの別帳票）は「一致」として通る。** 逆に**行数や表構造が変わる大きな版違い**は「不一致」に落ちうる（偽陽性）。※罫線1本の増減程度では落ちない——back/detail は期待線 42 本中 41 本が一致しても下限 15 を大きく超えるため（2026-09-02 検算）。`page_size_verdict` と同じ弱点を持つ
- 編集画面の挙動（3値別・FR-F04）:
  - **不一致** → 枠を描かない＋理由を案内＋「それでもこのテンプレートで開く」上書き操作を出す（FR-F05）。編集画面は送信が発生しない場なので上書きを許可する
  - **判定不能** → 現行どおり枠を描き、現行文言を維持する。ただし枠の描画を弱め、案内を強調する（FR-F08・Should）——「合っているように見える」誤読を避けるため
  - **一致** → 現行どおり
- 実行画面の挙動: **上書きは持たない**（理由は §9）。ページ単位で継続し（FR-F11）、`様式不一致` には FR-F01 専用の理由コードを持たせて既存バケツと分離し（FR-F09）、送信前に止まったことを画面で判別できるようにする（FR-F10）
- **全ページのスコアと理由コードを、一致・不一致を問わず中間データとログへ記録する**（FR-F12）。較正母集団の配線であり、記入値ではないので 01 §6.5 に抵触しない（qa_lead M-9①）

#### (b) ページ全体からの枠候補一括生成

- 面画像の全体を入力として、罫線から**表候補と単発欄候補の両方**を返す（architect M-8・designer M-4）
- 現行の限界（要件として超える対象）:
  - `detect_ruled` は `if len(h_lines) < 3: return None`（`grid.py:52-53`）で、**単発の1マス枠は必ず落ちる**。欄候補の生産経路が現行に無い
  - `H_COVERAGE = 0.50`（`projection.py:11`）は**領域幅に対する比率**。ページ全体を領域にすると閾値がページ幅の 50% になり、幅 1053px の detail ブロック（面幅 2490 の 42%）は本来届かない。左右2ブロックの行位置が揃っている偶然で通っている。「射影に閾値を掛けるには領域が要る／領域を求めるには射影が要る」の循環（architect M-9）
- したがって要件として次を定める:
  - **検出閾値は領域幅比ではなく `render_dpi` 由来の絶対長で表す**（FR-F15）。循環を切る。⚠️ **この絶対長の閾値は (b) の新経路にのみ適用し、`estimate_shift` の検出条件（`H_COVERAGE`／`V_COVERAGE` の値と使い方）は変更しない**（architect 2周目 M-2）——これらは `projection.py` の共有定数で `estimate_shift` も使うため、素直に書き換えると平行移動推定＝読み取り出力が変わり、NFR-F08・AC-F45・§9.1 と矛盾する
  - **線分（端点付き）を抽出する原始関数を新設する**（FR-F47・architect 2周目 M-3）。`line_positions` は射影ピークの中心座標しか返さず端点を持たないため、絶対長の閾値だけでは矩形に閉じられない。**方式はランレングス＋隣接行マージ＋ギャップ橋渡し**（v1.4 で確定）。**閾値 8 個はすべて `render_dpi` 由来の絶対長**（暫定値・AC-F16／AC-F17 で検算）。**`projection.py` は参照も変更もしない**——`estimate_shift` と共有すると読み取り出力が動く。**(b) は新しい画像処理を許す唯一の範囲**（§9.1）
  - **候補の採用は編集画面の切り抜き（carve／`resolveOverlaps`）を通さない**（FR-F19・v1.4）。編集画面は「後から置いた枠が勝つ」ため、候補をそのまま Field として足すと既存欄が削られ FR-F19 に違反する。既存枠と重なる候補は `overlaps_existing` を立てて**一括採用の対象外**にし、**個別採用のときだけ警告して人が決める**（FR-F20）
  - **候補の粒度**（FR-F16・v1.4 で条件を確定）: **表候補（ブロック単位）= 行 ≥ 2 かつ垂直レール署名が一致し等ピッチ（±2px）**／**欄候補 = 1行1列の閉じた矩形**。出荷テンプレは1テーブルに2ブロックあるため、ブロック単位にしないと候補数と人手工程が噛み合わない
  - **成立条件**（FR-F16）: 罫線が閉じた矩形を成す帳票。成立しない入力では候補ゼロを明示して返す（黙って空を返さない）
- 名前付けの負荷への対応（2026-09-02 ユーザー回答: 枠を引く手間と名前を付ける手間は同じくらい重い）: 課金の発生しない補助のみ In に置く——候補への連番仮名の自動付与と、表の列名の一括リネーム（FR-F24・Should）。**OCR による欄名推定は後段のまま**（4.2 (e)）

⚠️ **本節は本件の中核ではない**（Q-F18 で確定）。投入された紙は「今後扱いたい別様式」ではなく無関係な書類だったため、(t) が直接応えるのは目標フローの後半（複数様式の使い分け）であって元の要望ではない。それでも In に残し (b) より先に置く理由は §3.4 のとおり。

※ v0.3 の本節は FR 番号を1つずつずらして参照していた。v0.4 で §5.3 の表に合わせて訂正した。

- シフト量・罫線一致本数・残差、および (f) の吸着量と fail-safe 発動有無を中間データとログへ残す（FR-F31・FR-F43）

#### (f) 実行時のブロック単位吸着（最後段・既定 OFF・条件付き）

- ユーザー判断（Q-F4=B）どおり In に残す。ただし §3.4 の最後段・既定 OFF（Q-F7）・§3.5 の残存リスク明記を条件とする
- **単位はブロック**（architect 問い2）。`_table_geoms` はブロックごとに `TableGeom` を作っており、綴じ側の歪みで左右が違う量ずれる入力を吸収したいなら実体はブロック単位
- **吸着は y 軸のみで着手する**（v0.4・Orchestrator 判断。critic 2周目 Must-F・architect 2周目 M-4）。列間隙は全テンプレートで 0 であり、「列間隙 0 ＝ x へ 1px でも隣列に食い込む」を厳密に適用すれば **x 軸の安全な吸着量は 0**。v0.3 が置いた「最小列幅に対する割合」は、隣接欄への食い込み防止という目的から導いた値ではなく「機能させたい」という都合が根拠だった。x 軸の吸着は Q-03（実データ）受領後へ送る
- **x 軸が no-op なのは仕様である**ことを明示する（FR-F34）。実装漏れや許容幅 0 による偶然の no-op と区別できる状態にし、緑偽装にしない
- **y 軸の許容幅は行間隙で確定**——実測（2026-09-02）:

| テンプレート／テーブル | row_pitch | row_height | 行間隙 | 列間隙 | 最小列幅 |
|---|---|---|---|---|---|
| `chouhyo-v1` front/family | 113 | 105 | 8 | 0, 0, 0 | 50 |
| `chouhyo-v1` back/detail | 104 | 100 | 4 | 0, 0, 0, 0 | 105 |
| `formB-v1` visit | 80 | 70 | 10 | 0（実測・06 §3.4 の列幅 200/150/400 は接している） | 150 |

  **列は接しており列間隙は全テンプレートで 0。** `min(行間隙, 列間隙)` を許容幅にすると 0px になり、fail-safe が常時発動して吸着は永久に no-op になる。この状態でこそ「OFF と ON で出力が一致する」AC は確実に通る（緑偽装）。したがって:
  - **y 軸**: `row_pitch − row_height`（行間隙）。family 8px／detail 4px／formB visit 10px
  - **x 軸**: **今回は吸着対象外**（上記のとおり安全な量が 0 のため）
- **吸着を信用する下限をブロック単位で立てる**（FR-F34・critic Must-6・示唆4）。現行の下限は全テーブル合算の `need = max(2, ceil(len(exp) × 0.5))` で、ブロック単位にすると小さい表では下限 2 に張り付く。下限に張り付くブロックは最初から吸着対象外にする
- fail-safe（FR-F36）: 対応が取れない、または吸着量が許容幅を超えるブロックは**テンプレート座標へ戻す**。理由コード付きで記録する
- **部分 fail-safe を作らない**（v0.4・Orchestrator 判断。critic 2周目 Must-E）。**1ブロックでも fail-safe に落ちたら、その面の全ブロックをテンプレート座標へ戻す**（FR-F42）。同じ面に吸着したブロックと戻したブロックが混在する状態は、§3.3 の「片面失敗でページ全体を失敗」および D-25 の「半分だけ正しい状態を正常顔で出さない」と矛盾する。記録（FR-F43）と可視化（FR-F41）は落ちたブロック単位で残す
- ブロック単位の部分適用は、(c) の記録が貯まってからの後段候補とする（§10.3 Q-F15）

#### (d) 前方互換

- 判定関数のスコアは**テンプレート間で比較可能な無次元**（`matched/total` ∈ [0,1]）にする。`matched` の本数生値では argmax が作れない（architect S-2）
- 入力は「面画像」ではなく**「ページ画像＋テンプレート」**。面切りは判定関数の内側に置く（architect S-2）

### 4.2 Out of Scope（後段）

**(e) 印字ラベルからの欄名推定（OCR）** — 後段（Q-F2=A で確定）

- 理由: Vision への送信を伴い、テンプレート作成のたびに課金が発生する。誤った欄名は出力列の割当を誤らせ、01 §8 第1層「配置誤り1件で不合格」に直結する
- ⚠️ ただし 2026-09-02 のユーザー回答で「名前を付ける手間は枠を引く手間と同じくらい重い」ことが判明した。**(b) 導入後に名前付けの残作業量を実測し、その結果で (e) の着手を判断する**（§10.2 の前提作業として積む）

**(g) 面全体の拡縮補正（D-25 の拡張）** — 別立てでは作らず後段に残す

- 判断: (f) の一部としても、独立した補正段としても今回は作らない
- 理由（因果）: 拡縮の害は「面の端ほどズレが大きくなる」形で出る。ブロック単位の吸着 (f) は各ブロックをその場所の検出線へ合わせるので、面の端にあるブロックもその線に合う——**面全体の倍率を求めなくても、拡縮由来のズレが結果として吸収される**。同じ害に補正段を2つ重ねると、どちらが効いたのか切り分けられず、§3.2 で確保した切り分け手段が意味を失う
- ⚠️ **v0.2 にあった「倍率差 0.3% で面の端が約 7px」は撤去した**（architect M-5）。設計書の実測ではなく Orchestrator の算術推定（0.003 × 2490 ≒ 7.5px）だった。02 D-25 から引けるのは「detail の行間隙 4px で ±2px からラベル混入・±12px で元号誤選択・スケールは補正しない」のみで、これは**補正の必要性を示すが必要量は示さない**
- 後段に残す条件: (f) 導入後も**ブロックの内部**で先頭行と末尾行のズレ量が違う（＝表そのものが伸縮している）ことが (c) の記録で観測された場合

**(h) 確認なしのテンプレート自動選択** — 後段

- (t) で「候補提示・確定は人」までを In にした。**投入画像から自動でテンプレートを決めて読み取りまで進む**部分は後段に残す
- 理由: 誤選択は配置誤りに直結し、しかも人が気づく契機が無い。(a') の判定は幾何一致しか保証せず、幾何が同じ別帳票を通す（4.1 (a')）。この弱点を持ったまま自動選択に踏み込まない
- 後段で解く障害: `gui/src-tauri/src/lib.rs` の複数箇所に埋め込まれた `templates/chouhyo-v1.json`（06 露呈7）／`Editor.tsx` の front/back 2面固定（06 露呈6）／`core/chouhyo_ocr/paths.py:26` の `project_root()` マーカー（06 露呈5）

**(i) 罫線の無い帳票（下線のみ・自由記入）** — 対象外（Q-F3=A で確定）

- 理由: 位置合わせ・枠候補生成・吸着のすべてが罫線射影に乗っている。罫線が無い紙は判定の足場そのものが無く、別方式（文字ブロックのクラスタリング等）の設計になる
- **対象の紙に罫線があることが本件全体の前提条件**（§7）

### 4.3 恒久的に対象としない

- 枠の**意味付け**の自動決定（欄名・項目種別・出力列）。線から取れるのは幾何のみで、列契約は人が与える（01 §3.1 の列名はユーザー指定名であり、帳票の印字とは異なる）
- 毎ページの検出結果をそのまま読取枠に採用すること。かすれ・手書きの罫線跨ぎで箱数が変わり、「列構成は全ページ同一」（01 §8）が崩れる

## 7. 制約

### 7.1 前提と依存

- 技術スタック: Python コア（`core/chouhyo_ocr/`）＋ Tauri/React GUI（`gui/`）。判定・生成・吸着はコア側、画面は呼び出しと表示のみ（01 §5.10）
- CLI 単体で全機能を実行できる状態を維持する（01 §3.5）。GUI からしか使えない機能を作らない
- 出力契約は変更しない。列構成は全ページ同一、配置誤りは1件で不合格（01 §8 第1層／05 が正本）
- **対象の紙に罫線があること**が本件全体の前提（Q-F3=A）
- **様式判定が保証するのは罫線幾何の一致のみ**。幾何が同じで中身が違う紙は通り、版違い・かすれは弾きうる（4.1 (a')）
- 実データ（Q-03・Q-12）は未入手。検証素材は自作サンプルと様式B に限られ、**合成した歪みで測っているため実物のズレ量分布は未検証**
- 吸着は既存の読み取り経路（D-25）を変更する。方式の版は `ALGO_VERSION` "2" → "3" で管理する（D-26）
- **利用者テンプレートの場所は環境変数 `CHOUHYO_USER_DIR` で Rust から core へ渡す**（v1.3）。core は自前で探索せず、`paths.user_templates_dir()` が値を検証して使う。未設定時は `project_root()/templates_user/`（開発・CLI 単体）
- **新設する Rust コマンドは3つ**（`list_user_templates`／`read_user_template`／`save_user_template`）、**新設する core サブコマンドは2つ**（`match-templates`＝(t)／**`detect-frames`＝(b)**）。FR-F49（書き出し・取り込み）は既存のダイアログ経路で成立し新コマンドを要さない。`detect-frames` は Rust の白リスト3箇所への追加のみで新しい権限を要さない（§7.3）
- 予算・期限: **期限は設けない**（Q-F5＝指定なし・2026-09-02）。順序は §3.4 で確定

### 7.2 回帰ゲートの判定規則

基準値の正本は 03 §3。**本書は数値を転記しない。** 判定は次の4条件をすべて満たすこと。

1. **4項目すべて PASS**（pytest／gui logic／cargo test／`core-dist`）。`core-dist` の FAIL はゲート全体を FAIL にする
2. **全件 passed かつ passed 件数が 03 §3 の基準値以上**。skip の増加で件数が保たれる場合は不合格（件数のみでは判定しない）
3. **吸着の既定値がどちらであっても、既定・非既定の両モードで 1・2 を満たす**
4. **既存テストの期待値を書き換えて緑にしたものは合格に含めない。** `ALGO_VERSION` の "2" → "3" という直値の更新のみ許容し、更新したことを記録する

**素材依存 AC の扱い**（v0.4 追加）: sample-1／sample-2 など `.gitignore` 配下の素材を要する AC（AC-F04・AC-F30・AC-F45 ほか）は **L2（開発機・素材あり）で判定**し、既定ゲート（L1）の skip 率判定の母集団には含めない（`pytest.mark` で区別する）。素材が無い環境で恒久的に不合格になる状態を作らないため。レベルの定義は 03 §2 に従う。

⚠️ **ゲートが緑であることは吸着が効いている証拠にならない。** v1.0 時点で吸着が no-op になる経路は3つある: ①**x 軸は仕様として no-op**（FR-F34）②既定 OFF（FR-F39）③期待横線 4 本以下の表を含む面は対象外（FR-F35）。y 軸は現存テンプレート（family 8px／detail 4px／formB visit 10px）で効くが、**効いていることを示すのは AC-F30（ON と OFF で出力に差が出ること）だけ**であり、回帰ゲートではない。AC-F30 は L2 の合成素材を要するため（§10.2-2）、L1 が緑でも吸着の検証は済んでいない。

### 7.3 (t) が必要とするファイルアクセスの範囲

現行のパススコープ機構は、保存が `validate_template_target` → `check_scope`（ダイアログで選ばれた `.json` のみ）、読み取りルートが `editor_pages` に限定（#69・`4b3bf7b`）、既定テンプレートの読み取りが固定1パス。(t) は**ディレクトリ列挙**と**一括読み取り**という新しい権限を要求するため、範囲を次のとおり限定する。

**新設する Rust コマンドは3つだけ**（v1.3）——`list_user_templates`（列挙）／`read_user_template`（1件読み取り）／`save_user_template`（保存。**staged → コア `verify` → promote を Rust 内で通し切る**）。**列挙とパス検査はこの3コマンドの中だけで行い、core 側は渡されたパスを読むだけ**にする（権限の入口を1箇所に閉じる）。既存の書き込みコマンドのスコープは変更しない（§9.4）。

**(b) の `detect-frames` は Rust の新しい権限を要さない**（v1.4）——既存のサブコマンド実行経路に乗るため、**白リスト3箇所への追加だけ**で済む: `ALLOWED_SUBCOMMANDS`（`lib.rs:25`）／`allowed_flags`（同 37・`--input`／`--page`／`--dpi`／`--template`）／`TEMPLATE_ACCEPTING_SUBCOMMANDS`（同 127）。新しいコマンドもファイルアクセス範囲の拡大も伴わない。

| 操作 | 対象 | 制限 |
|---|---|---|
| 書き込み（FR-F26） | `app_data_dir()/templates_user/` **直下のみ** | §7.4 の名前検証を通ること。**`save_user_template`**（staged → `verify` → promote を Rust 内で通し切る）で行い、既存の `write_text`／`write_template_staged`／`promote_template`／`discard_staged` のスコープ（picked のみ）は変更しない |
| 列挙（FR-F28） | **`templates_user/*.json` のみ**（非再帰）・**`list_user_templates` のみが行う** | 出荷テンプレートは列挙せず、固定1件の既定候補として照合に加える（権限拡大を片側に閉じる）。**除外**: `*.saving.json`（`STAGED_SUFFIX`・`lib.rs:257`）／`*.bak`（`backup_path`・`lib.rs:970`）／**通常ファイル以外**（ディレクトリ・リンク） |
| 読み取り（FR-F28） | 上記の列挙結果＋出荷テンプレート1件・**`read_user_template` のみが行う** | **1件あたり 5 MB 上限**（暫定 ※Q-F13）・**件数上限は NFR-F09 と揃える**。超過・パース不能・スキーマ検証 NG は「不正」として一覧に出し、他の候補の照合を止めない |
| core 側（`match-templates`） | Rust から渡されたパスのみ | **core は列挙しない。** `CHOUHYO_USER_DIR` は `paths.user_templates_dir()` が値を検証して使う（未設定＝開発・CLI 単体では `project_root()/templates_user/`） |
| 読み取り（FR-F27・FR-F29） | 利用者が選択した1件 | 既存の選択経路に従う。FR-F29 は §7.4 の再検査を通す |

**リンク経由の範囲逸脱を全操作で再検査する**（#69 S-N3 と同型）。`lib.rs:386-395` は canonicalize の**結果にも** `is_safe_root` を通している——ジャンクションを1本挟むと生パスは普通のサブフォルダに見えるのに畳んだ先がドライブ直下になりうるため。同じ流儀で次を要求する。

- 書き込み・列挙・読み取りのいずれでも、**canonicalize 後の親ディレクトリが対象ディレクトリと一致すること**を再検査する
- **最終成分が reparse point（symlink / junction）なら拒否する**
- **`templates_user/` 自体が reparse point なら、保存も列挙も拒否する**

**絶対パスを外へ出さない**: webview へ返すのは表示名（相対名）のみとする。**ログへはファイル名も出さない**——Q-S1 によりテンプレートファイル名自体が機微情報になりうるため、ログは `template_hash` または匿名化 ID のみを残す（FR-F50）。

**実装時に security レビューを通す**（§10.2-6）。テンプレート JSON は座標定義であって記入値を含まないが、列挙と一括読み取りはアクセス範囲の拡大にあたるため。

### 7.4 テンプレート名の検証（許可リスト方式）

> NFC 正規化が畳むのは合成／分解の表現差（例: 「が」U+304C と U+304B+U+3099）だけで、全角・半角や同形異字（homoglyph）は対象外。NTFS は大小文字を畳むが正規化はしないため（本機実測・2026-09-02）、NFC を通さないと見た目が同じ別ファイルが共存する。正規化には既存依存の `icu_normalizer`（tauri 経由で解決済み・Unicode Consortium 提供）を直接依存へ昇格して使い、新規クレートは追加しない（security 判定 2026-09-02）。

**拒否リストではなく許可リストで検証する。** 「パス区切りと `..` を拒否」では Windows 予約デバイス名・末尾ドット／空白・`:`（代替データストリーム）・制御文字が通る。

| 条件 | 内容 |
|---|---|
| 文字集合 | 英数・全角文字（日本語等）・`-`・`_`・**中間のスペース**のみ |
| 長さ | 1〜64 文字（暫定 ※Q-F13） |
| 末尾 | ドット・空白で終わらない |
| 予約名 | **NFC 正規化後**に Windows 予約デバイス名（`CON`・`NUL`・`PRN`・`AUX`・`COM1`〜`COM9`・`LPT1`〜`LPT9`・`CONIN$` 等）と一致しない |
| 実装 | **Rust の純関数として実装する**（`cargo test` で表駆動に検証・AC-F51）。NFC 正規化は **`unicode-normalization` クレート**を使う。⚠️ **依存追加にあたり供給網レビューを通す**（§10.2-6 の security レビューに含める） |
| 禁止文字 | `:` と制御文字を含まない |
| 拡張子 | **`.json` はシステムが付与する。** 利用者入力に含ませない |
| 既存名との比較 | **NFC 正規化後に case-insensitive** で比較する（正規化後同名も検出する） |
| 出荷物との衝突 | **`templates/` に実在するファイル名**と衝突しない（`chouhyo-v1.json` の固定ハードコードにしない——出荷テンプレートが増減しても条件が追随するため） |

## 9. NG 事項（やらないこと）

### 9.1 判定

- 様式判定を「疑わしければ通す」側に倒さない。ただし**判定不能は不一致ではない**——線が取れていないだけの状態で枠を消すと、罫線がかすれた本物の紙で作業ができなくなる（4.1 (a') の3値）
- 様式判定に新しい画像処理を足さない。既存 `estimate_shift` の計算を再分類する範囲に留める
- 判定スコアの閾値を新規に較正しない。既存の `SHIFT_MATCH_RATIO = 0.5` を流用する（新しい閾値を作ると較正の母集団が無いまま Must が完成しなくなる）
- **実行画面には「それでもこの様式で読む」上書きを持たせない。** 理由: 実行は送信＝課金と、要配慮個人情報の外部送信を伴う。編集画面（送信なし）で上書きして確認できる経路と、テンプレートを選び直せる経路（FR-F27）の2つが用意されるため、実行時にも上書きを置くと「確認せずに押せる送信ボタン」を増やすだけになる。偽陽性で止まった紙は、編集画面で確認するかテンプレートを選び直して再実行する

### 9.2 枠候補

- 枠の欄名・項目種別・出力列を自動で決めない（線から意味は取れない）
- 候補生成で既存の確定枠を上書き・削除しない（FR-F19）。**候補の採用を編集画面の切り抜き（carve／`resolveOverlaps`）に通さない**——通すと「後から置いた枠が勝つ」規則で既存欄が削られる
- **重なる候補を黙って採用しない／黙って捨てない。** 一括採用からは外し、個別採用で警告して人に決めさせる（FR-F20）
- 毎ページの検出結果をそのまま読取枠に採用しない（列構成が入力に依存して崩れる）
- 候補への仮名付与に OCR を使わない（課金を発生させない）

### 9.3 吸着

- **吸着を「とりあえず動かす」側に倒さない。** 対応が取れない・許容幅を超えるときはテンプレート座標へ戻す（FR-F36）。ズレたまま正常ステータスで出すのが潰したい故障そのものであり、D-25 が「0 補正で素通ししない」と決めたのと同じ理由
- 吸着で枠の**個数や対応関係**を変えない。動かすのは既に定義された枠の位置だけ（§3.3）
- ON/OFF の切替と記録・照合を持たないまま出さない（§3.2）
- 面全体の拡縮補正を吸着と同時に入れない。同じ害に補正段を2つ重ねると、どちらが効いたか判定できなくなる（4.2 (g)）
- **許容幅の内側での誤吸着を検出できると書かない。** 検出手段は存在しない（§3.5）。既定 OFF・下限・差分一覧は緩和であって検出ではない

### 9.4 テンプレート

- 確認なしの自動選択をしない（4.2 (h)）。提示までが今回の範囲で、確定は人
- **既存の書き込みコマンドのスコープを広げない。** `templates_user/` 直下専用の新コマンドを設け、`write_text`／`write_template_staged`／`promote_template`／`discard_staged` の picked 限定スコープは変更しない
- **`tauri.conf.json` の `resources` に `templates_user` を足さない**（足すと利用者テンプレートが配布物へ混入する。`templates/` が同梱されているのは出荷物だから）
- **保存先をリポジトリ内・インストールディレクトリ内に置かない**（v1.3）。`app_data_dir()/templates_user/` はどちらの外にあるため、git 追跡も配布物混入も構造的に起こらない。⚠️ **開発・CLI 単体のフォールバック先 `project_root()/templates_user/` はリポジトリ内に落ちる**ため、そちらには `.gitignore` の明示行を追加する（`.gitignore:51` の `*.json` による偶然の無視に頼らない）
- **絶対パスを webview・ログへ出さない**（§7.3）
- `templates/chouhyo-v1.json` の直書き箇所のうち、**実行時のテンプレート注入以外**（リポジトリルート探索マーカー・バックアップ対象判定）を本件で整理しない（4.2 (h) の後段扱い）
