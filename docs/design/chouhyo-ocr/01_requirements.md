## 2. 背景・目的
紙保管の定型帳票（全項目手書き）を、検索・集計可能な形で納品する必要がある。
本ツールは Google Cloud Vision API で OCR を実行し、1帳票＝1行の Excel ブックを生成する。

**本業務はデータ入力であり、誤った値が混入した成果物は対価にならない。** 読めなかったことは人が直せるが、もっともらしい誤りは見逃されたまま残る。**空欄を出すコストより、誤った値を出すコストの方が大きい**——この非対称性を全体の前提に置く。したがって確信の持てないセルには値を出さず「〓」を置き、行ごとの〓個数（要確認セル数）で人が確認すべき箇所を絞り込む。**読めない箇所を推測で埋めない。**

## 3. 適用範囲・前提

### 3.1 対象帳票と抽出項目
- 様式はテンプレート固定・1種類。表面と裏面が1ページに上下合成されたスキャン画像。帳票1枚＝1ページ＝出力1行
- 全記入項目が手書き。画像左右端にリング綴じ穴、表面右下に黒塗り領域（抽出対象外・マスクのみ）
- ⚠️ 上記の画像構成は自作サンプル由来で、先方の実データでは未確認 ※要確認（Q-03）。異なる場合は上下分割仕様と「入力ページ数＝出力行数」の前提を書き換える
- 抽出対象は13項目:
  - 表面（本人）: 氏名（ふりがな）／生年月日／住所（郵便番号含む・欄は2段。2段の意味は ※要確認（Q-04）。郵便番号を独立列へ分離するのは ※解釈）／電話番号／会社名・屋号／所在地／備考欄
  - 表面（家族欄）: 続柄・氏名2・生年月日2 の3項目 × 最大10行（5行×左右2ブロック）。**左ブロック1行目の「本人」も記載のまま出力する**。この3項目を家族欄の全行とみなし10行分（60列）を展開する判断は ※解釈（ユーザー未確認・出力列の約3割を占める）
  - 裏面（明細）: 来店年月日・金額・品目 の3項目 × 最大26行（13行×左右2ブロック。正確な行数は無記入原本で確定 Q-12）
  - **列名はユーザー指定名を正とし、実物の帳票の印字とは異なる**。対応は 来店年月日＝**祈願年月日**／金額＝**初穂料**／品目＝**願意**／氏名2・生年月日2＝家族欄の**氏名・生年月日**。目検時は帳票側の欄名へ読み替える
- 生年月日の元号は印字「昭・平・令」を手書きの丸で囲む方式。1ページ最大11箇所（大正・明治の記載方法は ※要確認（Q-07））
- 左右2ブロックの読み順は「左→右」を仮置き ※解釈

### 3.2 業務フロー
1. 先方でスキャン済みのPDFを受領する（スキャンは先方完了済みの工程・本側で実施しない）
2. 本ツールで一括変換し .xlsx を出力する
3. 「要確認セル数」降順で〓セルを原本と突き合わせて手修正する（修正のたび数式で自動減算）
4. 要確認セル数の合計 0 を確認し、数式を値貼り付けで数値化して提出する

- 表裏合成の正当性（別人の表・裏の組合せ）は突き合わせキーがなく検証不能。既知リスクとして受容する

### 3.3 適用範囲外
恒久的に対象としない項目と、今回のリリース（v1）でやらないだけの項目を分けて記す。

**恒久的に対象としない**
- LLM 推論（予算制約。画像処理＋Cloud Vision で実現）
- OCR 精度の数値保証（実運用サンプル未入手で実測不能）
- 辞書照合による置換・読取値の推定/補完（元号推測・西暦変換・前行継承）

**v1 では実装しない（将来のMVPで扱う・§9）**
- ツール内の目検・修正UI（画像と抽出値を並べて〓セルを修正する画面）。v1 の修正は出力 .xlsx の直接編集で行う
- 差分更新・名寄せ・重複判定。v1 は一度きりの一括処理を対象とする
- **列割当の変更**（どの項目をどの列へ出すかを画面で組み替える機能。テンプレート編集GUI の一部機能）。v1 は列位置の表示のみで、列順は §5.6 の209列固定
- 注: **テンプレート編集GUI 本体は v1 スコープ（§5.10）。** 上の1件は、その中で v1 に入れない部分を指す
- ⚠️ **罫線の自動検出による枠候補の提示は v1 スコープへ移動した**（2026-08-27・ユーザー判断）。v3.7 まで本節で「v1 では実装しない」としていたものを §5.10 へ繰り上げた。理由は §5.10 に記す

### 3.4 失敗時の処理方針
- **失敗は行単位で扱い、実行全体を止めない。** 位置合わせ失敗・様式不一致・展開失敗（PDFから画像への展開に失敗）・送信失敗・未送信は「全項目〓（要確認セル数＝抽出対象列数）＋ステータス記録」の1行として出力し、次の帳票へ進む
- **入力ページ数＝出力行数** を処理の成否によらず常に維持する
- ※Q-03 の前提（1帳票＝1ページ）が崩れた場合、入力ページ数＝出力行数の関係式自体を再定義する

### 3.5 必須前提
- GUI 採用は 02 D-04 の判断による。一度きり運用という前提自体は変わっておらず、費用対効果の重み付けをユーザーが変更したもの（経緯は 02 §7.29）。**一度きり運用は v1 の対象範囲であり、将来の継続運用は §9 のMVPで扱う**

- WebView2 ランタイム（Tauri の描画層）。Windows 10/11 では標準搭載されるが、未搭載環境の扱い（同梱インストーラでの導入可否）は ※要確認（Q-23）
- Vision API 資格情報は OS 資格情報ストアまたは DPAPI で保護（平文保存不可）
- PDF入力時の画像展開に Poppler `pdftoppm`（既定案）。インターネット接続必須
- 出力先・中間データ保持先はクラウド同期対象外のローカルパス
- 要配慮個人情報（品目＝宗教活動の記録）の外部送信可は確認済み（2026-08-26・ユーザー確認）。Google 側のデータ取扱条件は ※要確認（Q-15）
- スキャン品質（dpi・二値化有無・圧縮形式）は Q-03 で確認する。二値化済み・低dpi だった場合の丸印判定の実現方式は設計フェーズで再評価する

## 5. 機能要件

### 5.1 ファイル取り込み
- 指定フォルダ内の PDF（一次形式・本線）・JPEG・PNG を処理対象として列挙する。対象外拡張子はスキップしログへ記録する
- PDF は 1ページ＝1帳票として扱い、ローカルで画像へ展開してから送信する（展開ツールの採否・代替は Q-03 の結果とあわせて設計フェーズで確定）
- 【Could】同一パスまたは同一ハッシュの取り込み済みファイルは対象へ追加せずログへ記録する

### 5.2 テンプレートと位置合わせ
- 上下合成画像を表面・裏面に分割し、**それぞれ独立して**傾き・位置を補正する（1枚全体への単一変換は不可）
- 綴じ穴帯・黒塗り領域をマスクする（抽出対象外・二値化閾値の決定にも用いない）
- 欄座標・表裏分割位置・除外領域・家族欄と明細の行数はテンプレートに定義し、コードへ埋め込まない
- テンプレートは**テンプレート編集GUI（§5.10）で作成・編集する**。あわせて JSON を直接編集する経路も残す——CLI 単体で全機能を実行できるという原則（§3.5）をテンプレートの作成にも適用し、編集GUI を唯一の作成経路にしない
- テンプレートに定義する各項目は**項目種別（文字ベース／選択式）**を持つ。文字ベースは OCR の読取値を、選択式は丸印など選択の判定結果を値とする。**抽出方式は項目種別で決まり、項目名の命名規則には依存しない**（元号は選択式の1例であり、特例ではない）
- 位置合わせ失敗・様式不一致は全〓行として出力し、次の画像へ進む

### 5.3 OCR実行と送信制御
- 1リクエスト＝1画像（＝1リトライ単位）。複数画像を束ねない
- 実行あたりの API 送信枚数上限を設定で指定する。到達で送信停止し、未送信分は「未処理（送信上限到達）」の全〓行として出力・次回再開対象とする
- レート制限・一時エラーは指数バックオフで再試行する（最大回数は定数）。超過は失敗記録して次へ進む
- 【Should】実行前に資格情報の存在・読取可否を検証し、不備時は開始せず対処方法を提示する（GUI 起動時は同じ内容を画面へ表示し、CLI 起動時は標準出力へ出す。資格情報の値はメッセージ・ログ・画面へ出さない）

### 5.4 元号丸印判定
- 「昭・平・令」の丸囲みを自前スコア＋閾値（設定可変）で判定し、5値を出力する: 昭／平／令（そのまま）、未選択・判定不能（出力上はいずれも〓・中間データでは区別して保持）
- 判定箇所は本人1＋家族欄各行の最大11箇所。空行と判定した家族欄行には実行しない
- **退避先**: 検証の結果いずれの判定方式も不成立の場合、元号セルを一律〓としてリリース可（列構成不変・目検で補完）。丸印判定の成立をリリース前提としない

### 5.5 値の扱い
- 記載されたまま転記する。推定・変換・継承・辞書置換をしない（明細の年は「H20」「R3」「7」等そのまま。品目・続柄に語彙制限なし）
- 金額のみ数値化する: 読点・空白を `,` へ正規化後、`^\d{1,3}([,.]\d{3})+$` に合致する場合のみ桁区切りとみなし除去・整数化。非合致・非数値・単位付きは〓（適用順は 02 D-01）
- 家族欄10行・明細26行を固定列として展開する。行数超過を検出した場合は黙って切り捨てず、警告ログ＋ステータス「超過あり」を記録する（検出定義は 02 D-06）
- 空行判定: 行内全欄の Vision 読取結果が空なら空行とし、全列空文字・一切の判定を行わない（インク量を測る画像処理は実装しない）。空文字は要確認セル数に加算しない。**判定が Vision の読取結果に依存するため、かすれ・薄い記入を空行と誤判定するリスクが残る**（残存リスクとして §8 第2層で扱う・02 §7.16）
- **行が空行でない場合、読取結果が空のセルは〓とする**（空文字にしない）。空文字が現れるのは空行と判定された行のみとし、記入行の未読取を「未記入」と区別できない状態にしない
- 低信頼セルは読取値を出力せず「〓」のみとする（閾値は設定可変）。複数語項目の信頼度は最小値を採用。読取値・信頼度は中間データへ保持する
- セルの3状態を区別する: 読取値／〓（低信頼・判読不能）／空文字（未記入）

### 5.6 出力
- **同一の中間データから .xlsx と .csv の2ファイルを同時に生成する**（同一タイムスタンプ・形式の選択制ではない）。**目検と客先提出は .xlsx を正**とし、.csv はシステム取り込み・テキスト処理に充てる。CSV 単独にしない根拠は 02 §7.4
- 1帳票＝1行の横展開で、**列構成は記入量によらず固定・209列**（管理6＋本人13＋家族欄60=10行×6列＋明細130=26行×5列）。管理列は 要確認セル数・最低信頼度・帳票ID・入力ファイル名・ページ番号・ステータス の6列で、**帳票IDは入力ファイル名とページ番号から生成し氏名を含めない**。なお**列構成の圧縮（繰り返し項目の集約・シート分割）は要検討事項**とし、設計フェーズで確定する（02 D-14）。それまでは本項の209列仕様を既定とする
- 生年月日は元号・年・月・日の4列に分割。繰り返し項目は `family_01_続柄` `detail_01_来店年月日_年` 形式の連番列名（管理列の構成・列分割・列名規則は ※解釈）
- 行頭の「要確認セル数」列に、抽出対象列の〓個数を出力する（〓の完全一致・管理列は範囲外）。**管理列が6列になったため、対象範囲は管理列5列の時点から1列ぶん右へずれる**。.xlsx は COUNTIF 数式とし、修正で自動減算・降順ソートで優先順位付け・SUM で合計確認。.csv は同じ値を静的な数値として書く
- 「最低信頼度」列に、その行のうち**〓でも空文字でもなく、項目種別が文字ベースのセル**の信頼度の最小値を出力する。該当セルが1つもない行は空欄とする。**項目種別が選択式のセル（元号など）は母集団に含めない**——選択式の判定値は OCR の信頼度ではなく自前スコアであり、尺度の異なる値を同じ最小値に混ぜると意味を持たない数字になる。**〓になっていないセルの中から silent error（高信頼と判定された誤読）の候補を絞り、抜き取り照合（§8 第2層）の優先順位付けに使う**——〓セルの信頼度は目検の役に立たないため対象外とする。セル型は他列と同じ文字列型とし、桁形式は 02 D-21 で確定する
- ステータス列の値（8種）: 正常／位置合わせ失敗／様式不一致／展開失敗／未処理（送信上限到達）／未処理（中断）／送信失敗／超過あり（複数該当は `;` 連結・失敗系を先に置く）
- .xlsx: 金額のみ数値型、それ以外は全列文字列型（先頭ゼロ保持）。〓セルには条件付き書式で背景色を適用する
- .csv: 全列をクォートし、BOM 付き UTF-8 で書く。**Excel で直接開くと型推論で先頭ゼロが失われるため、先頭ゼロの確認はファイル内容のテキストで行う**（02 §7.4）

### 5.7 出力先・命名
- 出力先フォルダを設定ファイルまたは GUI のフォルダ選択で指定する（GUI で選んだ値は設定ファイルへ保存し、次回起動時の既定値とする）。ファイル名はタイムスタンプで自動生成し（例: `output_YYYYMMDD_HHMM.xlsx`）、同名衝突を発生させない。衝突時分岐・実行時のファイル名指定・接頭辞接尾辞は設けない

### 5.8 再開と中間データ
- 進捗・読取値・信頼度・丸印判定スコアをディスクへ永続化する
- 再実行時は未処理・失敗分のみを送信し、処理済み分は再送信しない（この1規則で再開・部分再実行を兼ねる）
- 中断のトリガは2つ: プロセス終了（Ctrl+C 等）と、GUI の中断操作（§5.10 標準構成・【Should】）。**いずれも同じ結果になる**——中断分は「未処理（中断）」の全〓行として出力し、次回続行する
- 閾値変更後、**API へ再送信することなく**中間データから出力を再生成できる
- 入力ファイルは移動・改変・削除しない。設定は1ファイルへ集約する（〓閾値・丸印閾値・送信枚数上限・出力先・中間データ保持先・ログ出力先の6項目のみ）

### 5.9 ログ・診断
- `app.log`（操作・実行設定・処理結果・警告・回復処理）／`error.log`（エラー・失敗内容）。実行開始時に主要設定値を記録する
- **帳票の記入値は一切ログへ書かない。** 出力可: 入力ファイル名・ページ番号・帳票ID・項目ID・処理ステップ名・エラーコード・信頼度の数値・設定値。例外メッセージに変数値を含めない
- 終了時サマリの6項目: 処理枚数／出力行数／位置合わせ失敗枚数／API送信回数／要確認セル数総計／行数超過件数。**Must**（§5.10 GUI 最小構成の完了サマリ表示が Must であり、その表示内容をこの6項目とするため。中身を Should に依存させない）

### 5.10 GUI
**GUI は2画面で構成する: 実行画面（帳票を処理する）と、テンプレート編集画面（座標定義を作る）。** どちらも処理ロジックを持たず、Python コアの呼び出しとファイルの読み書きに徹する。優先度は画面ごとに独立して判定し、テンプレート編集を実行画面の最小構成へ混ぜない。

**実行画面**
- GUI は Python コアのサブコマンドを呼び出し、進捗と結果を表示する。処理ロジックを GUI 側に持たない
- 最小構成: 入力フォルダ選択／出力先選択／実行開始／進捗表示／完了サマリ表示（§5.9 の終了時サマリと同一項目）／出力フォルダを開く
- 【Should】標準構成（MVP 期間中に随時追加）: 設定画面（〓閾値・丸印閾値・送信枚数上限・出力先・中間データ保持先・ログ出力先）／一時停止・中断ボタン／エラー一覧表示

**テンプレート編集画面**（v1 スコープ・実行画面とは独立した機能群）
- 実装する範囲は次の8項目に限る: ①帳票画像の表示（ズーム・パン）②**枠候補の生成**——罫線の自動検出、または人がテーブルの外枠と行数・列数を指定しての等分割生成 ③**生成された枠をクリックして抽出対象／対象外を切り替える**。ドラッグによる矩形の作成・移動・リサイズも併用できる ④矩形への項目名と項目種別（文字ベース／選択式）の割り当て ⑤除外領域（綴じ穴帯・黒塗り領域）の指定 ⑥表裏分割位置の指定 ⑦選択中の矩形が出力の何列目に出るかの表示 ⑧テンプレートJSONの読み込み・保存
- ⑦は**読み取り専用の可視化**とする。列順は §5.6 の209列固定で決まっているため、項目名から列位置を引いて表示するだけ。**どの項目をどの列へ出すかを画面で組み替える機能は持たない**（§3.3）
- **②③を v1 スコープへ入れた理由**（2026-08-27・ユーザー判断で §3.3 から繰り上げ）: 枠を人がドラッグで引く方式は、行ピッチを目視で合わせることになり **1px の誤差が13行目で13px のドリフトになる**。行高が 56px 規模のため隣接行へ食い込み、要件 §8 第1層（行ズレは1件でも不合格）を人手の精度に賭ける構造になる。枠を「生成して選ぶ」形にすると、行位置が算術または検出から決まりドリフトが原理的に起きない
- **枠候補の生成器は2種を持ち、差し替え可能とする**: 罫線の自動検出（実物のスキャン品質 Q-03 次第で不成立になりうる）と、人が外枠と行数・列数を指定しての等分割生成。**自動検出が不成立でも等分割生成で運用が成立すること**を条件とする——検出の成否をリリース前提にしない（元号丸印判定 §5.4 と同じ扱い）
- **枠候補の生成は Python コアで行い、画面はその呼び出しと表示に徹する。** 画面が画像処理を持たない原則（本節「両画面に共通」）を崩さない
- この画面が行うのは**テンプレートJSONの読み書きと画像表示だけ**とする。OCR・位置合わせ・丸印判定を画面側で実行せず、中間データ・出力ファイルも書き換えない
- **未保存の編集内容がある状態で、画面を閉じる・別の画像を読み込む・別のテンプレートを開く操作を行った場合は、破棄してよいかの確認を表示する。** 自動保存はしない（保存は利用者の明示操作とする方針を、`purge --yes` や出力ファイル名の扱いと揃える）

**両画面に共通**
- CLI 単体で全機能を実行できる状態を維持する（自動化・デバッグ・GUI 不調時の退避路）。GUI からのみ実行できる機能を作らない。テンプレートについても、編集画面で作れるものと同じ内容を JSON の直接編集で作れる状態を保つ
- GUI と Python コアの進捗受け渡し方式は設計フェーズで確定する（02 D-16）。テンプレート編集画面の実現方式（画像描画・PDFの画像化・列位置の引き方・JSON検証の置き場所）は 02 D-22 で確定する

## 6. 非機能要件
- **6.1 性能**: 物理メモリ8GBの Windows 端末で100枚連続処理を OOM・停止なく完走すること
- **6.2 信頼性**: 中断後の再開で処理済み分を再送信しないこと（送信中に中断した1枚のみ再送を許容・02 D-05）。送信枚数上限が実効的に機能すること。同一の中間データ・設定での再出力結果が完全一致すること。列構造が入力内容に依存しないこと。どの失敗でも再実行判断に必要な情報（ステータス・ログ・中間データ）が残ること
- **6.3 保守性**: 中間データは正常完了後も保持し、削除は明示操作のみで行うこと（保持期間の既定値は ※要確認（Q-14））。テンプレート・設定をコードから分離すること
- **6.4 互換性**: Windows デスクトップで動作すること。日本語ファイル名・UTF-8・異体字（﨑・髙 等）を含む環境で実行できること。GUI は WebView2 ランタイムを前提とする（未搭載環境の扱いは Q-23）。配布形態は Tauri が生成する Windows インストーラとし、GUI・Python コア・Poppler を1つの導入手順で配置すること（配布物のサイズ・コード署名の要否は Q-25）
- **6.5 セキュリティ・個人情報保護**: ログ・テキスト形式一時ファイルに記入値を残さないこと。中間データ（要配慮個人情報含む）のアプリ側暗号化の要否は設計フェーズで判断し根拠を記録すること（02 D-07。実行端末のディスク暗号化の状況は ※要確認（Q-21））。資格情報を平文保存しないこと。開発・単体検証は無記入原本と自作サンプルのみとし、実データは指定端末のみで扱い検証後に削除すること

## 7. 入出力・永続化仕様
- 入力: スキャン画像（JPEG / PNG）・PDF。処理後も無変更で保持する
- テンプレート: 座標定義ファイル（欄座標・表裏分割位置・除外領域・マスク幅・行数・項目種別）。**テンプレート編集GUI（§5.10）で作成・編集する**。JSON の直接編集でも同じ内容を作れる
- 設定: 設定ファイル1つに集約（上記6項目）
- 中間データ: 進捗・読取値・信頼度・丸印スコア・PDF展開画像。**記入値（個人情報・要配慮個人情報）を含む**ため、同期対象外パスに置き削除は明示操作のみ
- 出力: `.xlsx` と `.csv` の2ファイル（同一の中間データ・同一タイムスタンプ）。.xlsx は〓セルに条件付き書式・要確認セル数は COUNTIF 数式、.csv は全列クォート・BOM 付き UTF-8・要確認セル数は静的な数値。目検と提出の正は .xlsx
- ログ: `app.log`／`error.log`（記入値を含めない）

## 8. 受け入れ条件
品質は2層で判定し、**ツールが担保するのは第1層のみ**（受け入れの主役）。

- **第1層（配置の正しさ・ツールが担保）**: 枠内の記入値が正しい列・正しい行に置かれること。欄の対応誤り・行ズレ・左右ブロック順序誤り・表裏混線・隣接欄混入は構造欠陥として**1件でも不合格**。記入内容が既知の自作サンプルで検証する（Vision 精度に依存せず判定可能）。枠を大きく逸脱した記入の隣接列混入のみ対象外とし、低信頼なら〓化して第2層へ渡す。**本番実行時に配置誤りを自己検出する仕組み**の方式は設計フェーズで確定する（02 D-15）。**第1層の合格は自作サンプルによる暫定合格**であり、Q-03／Q-12 の解消後に Q-16 パイロットで配置基準（欄対応・行ズレ・表裏混線）を本番データで再検証してから運用を開始する（02 D-15）
- **第2層（内容の正しさ・保証対象外）**: 読取文字の正誤は担保せず数値目標も置かない（客先にも明示）。〓化・要確認セル数・人の修正・抜き取り照合でカバーする。残存リスクは silent error（高信頼と判定された誤読）であり、〓ゼロの行も抜き取りで原本照合する。重点は氏名・ふりがな（異体字の常用字体化）と空行判定された家族欄行。抜き取り率は処理規模の確定後に決定する ※要確認（Q-01）

合格条件（無記入原本＋自作記入サンプルで検証。詳細な受入基準は 02 第1章）:
1. 【第1層】既知サンプル（家族欄4行以上・明細10行以上・左右両ブロック記入）で全値が期待する列・行に一致し、取り違えが0件であること
2. 13項目が対応列へ展開され、出力行数＝入力ページ数がどの失敗時も維持されること
3. 低信頼セルが〓化され読取値が出力に残らず、要確認セル数で修正対象を特定・ソートできること
4. 元号丸印が5値で判定され最大11箇所が反映されること（判定不成立時は一律〓でリリース可能であること）
5. 金額の桁区切り判定・整数化が機能し、転記主義（推定・辞書置換なし）が守られること
6. 閾値変更後に API 再送信なしで再出力でき、〓の数が変化すること
7. 中断→再実行で未処理・失敗分のみが送信され、処理済み分が再送信されないこと
8. 〓セルに背景色が付き、電話番号・郵便番号・年月日が文字列型で先頭ゼロを保持していること
9. ログ・一時ファイルに記入値が残らず、資格情報の平文保存がないこと
10. 提出前に要確認セル数の合計 0 を確認する運用が成立していること
11. 【GUI 最小構成】GUI から入力フォルダと出力先を選んで実行を開始でき、処理中に進捗表示が更新され、完了後にサマリが表示され、出力フォルダを開けること。同じ処理を CLI 単体でも実行でき、出力が一致すること
12. .xlsx と .csv が同一実行で生成され、管理列を除く抽出対象列のセル値が両者で一致すること。CSV の先頭ゼロ保持は**ファイル内容をテキストとして読んで判定する**（Excel で直接開いた表示では判定しない）
13. 最低信頼度列に、〓でも空文字でもなく項目種別が文字ベースのセルの信頼度の最小値が出力され、選択式セルの値が採られず、該当セルが無い行は空欄であること
14. 【テンプレート編集GUI】画面で画像を読み込み、枠を生成または描画して抽出対象を選び、項目名・項目種別・除外領域・表裏分割位置を指定して保存したテンプレートで `run` が完走し、出力行が生成されること。**エディタが書き出したJSONをコアがそのまま読めること**——エディタ専用の読み込み経路・変換工程をコア側に作らない
15. 【テンプレート編集GUI】画面で指定した除外領域が抽出対象外として扱われ、二値化閾値の決定にも用いられないこと（§5.2 の規定が、GUI で作ったテンプレートでも手書きJSONと同じに成立すること）
16. 【テンプレート編集GUI】**等分割生成**で作った枠が、行数から算術で決まる位置に並ぶこと（行ピッチのドリフトが生じないこと）。生成された枠をクリックして抽出対象／対象外を切り替えられ、対象外にした枠が出力列に現れないこと
17. 【テンプレート編集GUI】**罫線の自動検出**が枠候補を返すこと。**返さない場合でも等分割生成でテンプレートを作成でき、`run` が完走すること**——自動検出の成立をリリース前提にしない（§5.10）

## 9. 将来の拡張（MVPロードマップ）
**目的**: 今回の様式1種類に固定したツールを、様式に依存しない汎用帳票ツールへ展開する。v1 はテンプレート・出力レイアウト・座標定義をコードから分離してあるため、様式を追加する余地が残っている。

**第2段階の候補機能**（いずれも v1 では実装しない）
1. **テンプレート編集GUI の残り部分**（**本体は v3.6 で v1 スコープへ移動済み・§5.10。罫線の自動検出も v3.8 で v1 へ移動**）。将来へ残すのは2点: ①**列割当の変更**——どの項目をどの列へ出すかを画面で組み替える。v1 は列位置の表示のみ ②様式を識別するメタ情報（様式ID・版）の付与
   - なお v1 の罫線自動検出は**自作サンプルでしか検証できない**（Q-03 未入手）。実物のスキャン品質が判明した時点で閾値・カーネル幅の再調整が要る見込みであり、その再調整は第2段階の作業に数える
2. **目検・修正UI**: 原本画像と抽出値を並べて表示し、〓セルをその場で修正する。修正結果を中間データへ書き戻し、.xlsx と .csv を再出力する
3. **複数様式の登録と自動判別**: テンプレートを複数保持し、投入画像がどの様式かを判別して振り分ける
4. **継続運用・差分更新**: 追加分の取り込み・名寄せ・重複判定を扱う

**v1 の設計判断のうち、この展開を塞がないもの**
- 欄座標・表裏分割位置・除外領域・行数はコードへ埋め込まずテンプレート（座標定義ファイル）へ外出ししてある（§5.2・§6.3）。v1 のテンプレート編集画面が書き出す先がこのファイルであり、様式が増えても書き出し先の形は変わらない
- 位置合わせで罫線検出を実装した場合（02 D-13）、その検出処理は上記①の枠自動判定へ流用できる（流用先の画面は v1 で先に存在することになる）
- 出力レイアウトは差し替え前提の要検討事項として保持している（02 D-14）。様式ごとに列構成が変わる展開と衝突しない
- 項目種別（文字ベース／選択式）を v1 からテンプレート属性として持たせてある（§5.2）。v1 のテンプレート編集画面が枠ごとに種別を指定する（§5.10 ③）

**段階を分ける理由**: v1 は先方の実データ（Q-03・Q-12・Q-16）が未入手のまま設計しており、様式1種類でも前提が崩れる余地が残る。1種類で通し運用を成立させてから汎用化する。v1 で守るべき制約の確定は 02 D-20。
