### 2.2 その他の判明事実

- **全項目が手書き**（印字は帳票ラベルのみ）→ Vision の日本語手書き精度が全項目に効き、目検は全項目対象が既定路線
- **表裏が1ページに上下合成済み** → 「4枚1セットの紐付け」問題は消滅。代わりに「上下領域分割」「合成事故の検出不能性」が発生（§5.4）
- リング綴じ穴が左右端に写り込む → スキャナ取込 ※推測。端部ノイズ・綴じ辺湾曲の懸念（§5.6）
- **表記揺れの実例**: 年=元号なし裸数字（7/8/9/10/17）と「H20」「R3」プレフィックス付きが混在／金額=「10,000」「10.000」（ピリオド区切り）「100」「1000」混在／願意は少数語彙（家内安全・厄除・交通安全・合格祈願・七五三の5種を確認。母集合ではない ※推測）
- 明細に H20〜R3 の年代が混在 → この帳票は**追記され続ける台帳**の可能性（§3 NB1に直結）※ダミーデータのため実運用を反映しているかは要確認

## 3. 新ブロッカー（設計着手前に決める3件）

### NB1. 一度きりの一括デジタル化か、継続運用か

裏面明細は来訪ごとに追記される構造。ここが要件の性格を決める最大の分岐。

| パターン | 内容 | 影響 |
|---|---|---|
| A. 一度きりの棚卸し | 過去分の一括デジタル化。以後は別管理 | 重複問題は二重投入のみ。スコープを大幅に削れる |
| B-1. 継続・全件洗い替え | 再スキャンごとに全明細上書き | 実装容易。ただし前回目検で人が直した内容が上書きで消える事故 |
| B-2. 継続・差分追記 | 新規明細のみ追加 | 明細の同一性判定が必要。同日・同額・同願意の正当な重複がありうるため判定不能ケースが残る |

カードに帳票番号等の一意キーは観察上見当たらない ※要確認（黒塗り部が該当する可能性）。キーがないと名寄せは「氏名＋生年月日」頼みになり、氏名の誤読で同一人物が2件に分裂する。**ユーザー回答「1画像1行だから取り違えは少ない」はパターンAでは成立するがBでは成立しない。**

### NB2. 出力の受け手と行粒度 — 「1帳票=CSV1行」は目検が破綻する

列数試算（※概算）: 表面基本 約14列＋家族10行×6列=60＋明細26行×5〜6列=130〜156で**素の合計 約204〜230列**。raw併記・信頼度カラムを足すと最大数百列。Excelの列上限には収まるが、**横スクロール数百列から誤読を探す目検は成立しない**。全項目手書き＝全項目目検対象の前提と正面衝突する。

**推奨案: 3テーブル分割**（内部データモデルは常に正規化し、フラット化は出力層に閉じる）

| ファイル | 行の粒度 | 列数 ※概算 |
|---|---|---|
| person.csv | 1帳票=1行 | 約20 |
| family.csv | 1家族メンバー=1行 | 約8 |
| detail.csv | 1明細=1行 | 約7 |

- 帳票IDは「入力ファイル名＋ページ番号」から生成（氏名を含めない）。Excel納品なら1ブック3シート
- 横展開を選ぶ場合: 列数は設定値で固定（家族10・明細26）、超過時は黙って切り捨てず警告付きで溢れさせる。列名は `family_01_relation` 等のゼロ埋め連番
- **行粒度は出力の受け手（人が読む台帳か、別システム取り込みか）で決まる**。取り込み先があるならそのスキーマから逆算

### NB3. 要配慮個人情報の該当性（B1「確認済み」への追加確認）

サンプルにより帳票が神社の祈願者カードとみられることが判明 ※推測。**「願意」は本人の宗教活動に関する記録**であり、個人情報保護法上、信教に関する情報は要配慮個人情報に分類される。祈願者名簿がこれに該当するかは法的判断が必要 ※要確認。該当する場合、取得時同意・第三者提供の制限が加わり、**外部API送信の整理がB1の確認水準では足りない可能性がある**。

- ユーザーの「外部送信OK確認済み」が、**願意（宗教情報）を含む前提での確認だったか**の再確認が必要
- 1画像=表裏合成で、1リクエストに最大11人分の氏名・生年月日・続柄＋最大26件の宗教活動履歴が載る。情報密度が前版想定より高く、ログ・ダンプ流出時の被害も大きい

## 4. 受入基準の進め方（2段階方式・PM提案）

**段階1（いま合意する）= 測り方の定義／段階2（スパイク実測後）= 数値の確定。** 実測ゼロで数字を置くと根拠なき目標が一人歩きするため、数値は実測後に埋める。

- 母数: 実運用帳票 N≧30 ※経験則（複数人の筆跡・古い記入を含む。**ダミーサンプルは精度実測に使わない**）
- 単位: フィールド単位の完全一致率。**分母は「記入がある欄」**（空欄を正解に数えると空欄率の高いこの帳票では精度が水増しされる）
- 項目を難易度3階層（易=願意・月日／中=初穂料・祈願年月日／難=氏名・ふりがな・続柄／最難=住所・備考）に分け階層別に目標を置く。単一の全体目標は不可
- **繰り返し項目は帳票単位の合格率も併記**: 丸印11箇所の箇所単位99%でも、11箇所全正解の帳票は約89%（95%なら約57%）※独立仮定の概算。「丸印99%」だけで合意すると「10枚に1枚はどこか間違う」状態を見逃す
- **精度と独立の合否条件2つ**:
  1. silent error 抑制: 「高信頼と判定した中の誤り率」を別建てで計測（低信頼フラグ付きで目検に回る誤りは実害ゼロ、高信頼の誤りが実害の全て）
  2. **行整合（行ズレ）ゼロ**: 家族3行目の氏名が4行目に入る・左右ブロックの読み順誤りは「別人の生年月日が紐づく」事故。1件でもNoGo扱い

## 5. 技術要件の更新（サンプル反映）

### 5.1 丸印判定の再定義

- 対象は「空欄への記入」ではなく**「印字漢字（昭・平・令）を囲む環状ストロークの検出」**。単純減算では位置合わせ誤差が印字漢字の残差として出るため、判定領域を「各文字の外接矩形の外側〜セル境界の環状帯」に限定する方式を第一候補とする
- 出力は5値: `昭 / 平 / 令 / 未選択 / 判定不能`（全候補が閾値未満=未選択、上位2候補の差が閾値未満=判定不能。前者は帳票の事実、後者はツールの能力限界で業務上の扱いが異なる）
- **元号コード体系は開いた体系**（M/T/S/H/R/OTHER/UNKNOWN）にする。印字選択肢に大正がなく、大正・明治生まれの記載方法が不明（§7 Q12）
- **空行判定を先に行い、空行に丸印判定を走らせない**（空行への誤検出防止。行内全セルのインク量閾値で判定）
- 家族行の元号セルは数mm規模 ※推測。**必要dpiは丸印の環状帯幅から逆算**する（dpiは自由変数ではなく丸印判定から降りる制約）
- 方式は減算ありきで固定せず、(a)環状帯インク密度 (b)セル画像の軽量ローカル分類器（LLM不使用制約に非抵触） (c)テンプレート減算 の3案を実サンプルで比較。教師データは1枚から11箇所取れる（50枚で550サンプル）

### 5.2 正規化ルール（不変条件つき)

**全項目を raw（原文保持）と normalized（正規化値）の二本立てで出力する。** 正規化は情報を落とす方向の変換で、raw がなければ誤りが不可逆になる。raw があれば正規化ルール改善後にAPI再送信なしで再変換できる。

不変条件:
1. 正規化処理は raw を書き換えない
2. 推定・補完値には derivation フラグ（`ocr`/`dictionary`/`inherited`/`inferred`）を必ず立てる
3. 「空」を一種類にしない: 全項目に**空欄/読取不能/読取値あり**の3状態（丸印の未選択/判定不能と同思想）
4. 黙って情報を捨てない（上限超過・辞書外・レンジ外は可視化）

個別ルール:
- **年**: 裸数字の年（「7」）は平成7か令和7か原理的に確定不能。推定して西暦化せず `era=UNKNOWN` で保持。生年月日は丸印判定結果と裸数字を結合し、**丸印が判定不能なら生年月日全体を未確定として扱う**（フィールド間の不確実性伝播）。前行からの継承補完を使う場合は `inherited` フラグ必須。そもそも西暦確定が必要か・記載のまま転記でよいかを先に確認（§7 Q7）
- **改元跨ぎの矛盾検出**: H31年5月以降・R1年4月以前・S64年1月8日以降は存在しない日付→要確認フラグ。未来日チェックも。日付は数少ない機械的検算可能項目
- **元号表記辞書**: 丸印選択/H20型/令7型/令和3年型/裸数字を単一内部表現へ。OCR誤読候補（H↔日、S↔5/8等）は実測で確定
- **金額**: 区切り記号（`,` `.` `、` 空白）は全て除去して整数化（初穂料に小数は実質ない ※経験則）。妥当性レンジ（下限・上限）を業務確認して設定しレンジ外はフラグ。**金額は誤読の機械的検出手段がないため目検必須項目に指定**
- **郵便番号突合**: 郵便番号から復元した都道府県・市区町村とOCR住所を突き合わせ、最難関の住所欄の誤読検出・部分補完に使う（郵便番号辞書のライセンス・更新は法務確認）
- **異体字**: 﨑・髙・邊等とサロゲートペア（𠮷）が出る前提。raw に原字・normalized に新字体で両立。**納品先システムが原字を受け取れるか**を先に確認
- **反復記号**（〃・同上・々）: 台帳形式ゆえ出現可能性が高い ※経験則。前行継承（`inherited` フラグ付き）か raw のまま出すかを決める

### 5.3 辞書照合（願意・続柄）

- 願意は有限集合の可能性が高く、手書き崩し字への最大の武器。**辞書はコード埋め込みでなくユーザー編集可能な外部ファイル**とし、辞書外語の出現は件数ベースで把握
- 観測5語を母集合と見なさない（安産祈願・商売繁盛・車祓等の存在可能性）。神社側のマスタ（料金表等）があれば初期辞書に
- **同着・閾値未満は近い語へ丸めない**: 語尾共通（〜安全×2、〜祈願×2）で識別情報が先頭2文字に集中。先頭不読なら「辞書外」として raw のまま出す
- 辞書は誤りを正しい語に化けさせる（目検で気づけない）ため、**生OCR精度と照合後精度を分けて計測**
- 続柄（父・母・妻・長男…）にも同じ仕組みを適用

### 5.4 テンプレート構造と表裏合成

- **罫線グリッド検出を位置合わせと欄定義の共通基盤に据える**（推奨）。欄は概算140個あり座標手打ちは非現実的。罫線グリッドから行×列を自動生成し、定義は「テーブル位置＋列の意味」に縮める。罫線のかすれ・欠損は検出済み罫線からの等間隔補間で復旧。※表面上部が罫線囲みかアンダーライン形式かで成立性が変わるため現物確認要
- **テンプレートは3層**: ページレイアウト定義（上下分割）／面テンプレート（表・裏）／欄座標。合成時の表裏の傾き・位置は独立にずれるため、**上下分離後に面ごとに独立で位置合わせ**。1枚全体に1変換では表裏どちらかが必ずずれる
- **合成事故（上下逆・片面のみ・別人の表裏合成）はツール側で検出できない**（共通キーがない場合）。黒塗り部が整理番号なら検証キーに使える。使えないなら「表裏対応の正当性は入力側運用で担保・ツールは検証しない」と責務境界を要件に明記（無言の前提はレコード取り違え=個人情報漏洩に直結）

### 5.5 送信単位（「4画像1送信」の廃止）

- 表裏合成で1画像が縦長・高解像度化し、単体でVisionのサイズ上限に近づく ※要確認。4枚束ねの余地が狭い
- 1リクエスト4帳票は、1帳票の失敗で4帳票分再送=課金4倍・再開単位も複雑化
- **要件を「1リクエスト=1画像=1リトライ単位、並列度N、1実行あたり上限枚数」に置き換える**

### 5.6 入力品質

- **スキャナ側の二値化禁止・グレースケール8bit以上**で取得する運用を要件に固定（二値化はスキャナ側で不可逆。丸印判定に中間調が必要。古い帳票の黄ばみ・褪色に固定閾値は使えない）
- **スキャナ一次出力の確認**: PDF経由なら内部画像がJPEG再圧縮されている可能性があり「無加工原画像」が最初から存在しない（前版で指摘した圧縮×減算方式の競合が入力段階で発生）。無圧縮/可逆設定への変更可否、PDF→画像のローカル展開工程（Vision の PDF 非同期API経路の回避を兼ねる）
- **リング穴の写る画像端の帯を前処理マスク**（マスク幅は最外周欄との位置関係を実測して固定。家族テーブルが左右端に近いため広すぎると欄を削る）
- **綴じ辺湾曲の実測**: 綴じたままスキャンなら湾曲歪みはアフィン/射影で補正不能→罫線ベースの局所補正が必要。運用を「外して平置き/ADF」に変えられるなら画像処理の規模が大きく下がる
- 巨大な黒塗り領域はヒストグラム系の二値化閾値決定を歪めるため前処理の除外領域に指定
- 記入ペン色を運用指定できるなら（新規記入分のみ）、カラー取得＋色チャンネル分離で印字/記入の分離が桁違いに楽になる（検討価値あり）

### 5.7 スコープ整理（PM判定・現時点）

| 区分 | 項目 |
|---|---|
| Must | 表面本人情報抽出／明細抽出／合意した行粒度での出力／3状態+低信頼フラグ／目検工程／**行整合ゼロ** |
| Should | 家族テーブル抽出／元号丸印判定（最大11箇所）／願意・続柄の辞書照合 |
| Could | 住所2段目／備考／電話番号（記入率次第 ※要確認） |

### 9.2 横展開＋〓運用の派生仕様（要件化する）

- **行頭に「要確認セル数」列を置く**: その行に含まれる〓の個数を出力。この列の降順ソートで「直しが必要な帳票」順に並ぶ。200列超を横断した〓検索を回避する（「〓でソートして修正」の運用を成立させる中核仕様）
- **Excel出力時は〓セルへ条件付き書式（背景色）を自動適用**（横スクロール中の見落とし防止）
- **〓閾値は config で可変**。閾値変更後に**API再送信なしで再出力**できるよう、読取値・信頼度は再開用永続データに保持する（出力ファイルには載せない。B3で許容済みの永続化の用途に追加）
- 信頼度の限界を要件に明記: Vision の confidence は手書きに対する較正が保証されない ※要確認。**高信頼の誤り（silent error）は〓にならない**ため、受入基準の抜き取り検査（§4の2段階方式）は〓運用があっても省略しない
- 複数語にまたがる項目（住所等）の信頼度集約は**最小値**を採用（1語でも怪しければ〓に倒す安全側）
- **丸印（元号）にはAPIの信頼度が存在しない** → 自前スコアに閾値を設け、「未選択」「判定不能」は〓扱いで出力（5値定義は§5.1のまま）
- 列は**固定長**: 家族10行分・明細26行分を常に出力（設定値）。超過時は黙って切り捨てず警告＋あふれ処理。列名はゼロ埋め連番（`family_01_続柄` 等）
- CSV選択時の注意: 〓は文字として機能するが、セル背景色・文字列書式は使えない。電話番号・郵便番号の先頭ゼロ保持のため全列クォート出力とし、目検作業はExcel推奨と要件に明記
