## 1. 総評

ドラフトは「何を抜き取るか（出力項目）」と「機能の箇条書き」は具体的に書けているが、要件定義書の構造で見ると **入力（どんな画像が来るか）・業務（誰がどう使い、出力を誰に渡すか）・完了（どうなったら合格か）の3領域がほぼ空白**。このまま設計に入ると、以下の3点で高確率で手戻りが発生する。

1. 受入基準（精度目標）がゼロで、完了判定が不可能
2. 個人情報の外部API送信の可否が未検証で、NGなら Cloud Vision 前提の設計が全損する
3. 「OCR結果はメモリ内で破棄」と「失敗地点から再開」が設計上矛盾している

## 3. ブロッカー級の指摘（回答・確認が済むまで設計に入らない）

### B1. 個人情報の外部API送信の法的・契約的整理

抽出項目（氏名・ふりがな・生年月日・住所・電話番号・続柄・勤務先）は個人情報の塊であり、続柄＋来店履歴・金額が結合すると家族構成と取引履歴が復元できるデータセットになる。これを Google Cloud Vision へ送信する構成だが、以下が未整理。

- 個人情報保護法上の「委託」構成の整理。委託元との契約における再委託（Googleへの提供）条項・安全管理措置・事故時の責任分担・契約終了時のデータ消去義務の確認
- 帳票記入者本人への利用目的の通知に、外部クラウドでのOCR処理が含まれているか
- Google Cloud 側のデータ取り扱い条件の確認（※すべて要確認・原文未確認）: 送信データの保持期間／機械学習利用の有無とオプトアウト／処理リージョン（越境移転）／human review の可能性／DPA相当の契約条項の適用可否
- NGだった場合の代替方針（ローカルOCRエンジン／プロジェクト中止）を要件の分岐として持つこと

確認結果によっては Cloud Vision 前提そのものが崩れる。**最優先で着手すべき項目**。契約書・規約の最終解釈は弁護士または法務部門へのエスカレーションが必要。

### B2. 現物サンプルと精度実測なしに要件を確定できない

- 帳票の現物サンプル（表・裏・数種類）がないと、テンプレート方式・丸印判定方式の成立可否すら検証できない
- Cloud Vision の**日本語手書き**認識の実精度は未検証 ※要確認。実サンプル数十枚を投げて項目別の素の精度を測ることが、受入基準設定の前提になる
- 様式が何種類あるか・旧様式が混在するかで、テンプレート方式の成立性が変わる
- テンプレート座標の基準となる原本（印刷データまたは無記入帳票の高精度スキャン）を入手できるかが、位置合わせと丸印マスク作成の両方の前提

### B3. 受入基準（精度目標）がゼロ

- OCRは100%にならない。項目単位で「何%正しく取れたら合格か」を決めないと、納品後に「使えない」と言われる余地が残る
- 単一目標値（例: 全体95%）は不可。難易度が項目間で桁違い（丸印・日付=易／電話番号・金額=中／住所・氏名・備考欄=難）のため、**項目別の目標値**＋目検で必ず人が見る項目の指定が必要
- 「レコードの取り違え」（A氏の帳票の住所がB氏の行に入る）は精度不足ではなく**個人情報漏洩**として、独立した重大欠陥に区別すること
- 目標に届かなかった場合にリリースするか否かの判断基準も先に決める

### B4. 「メモリ内で破棄」×「失敗地点から再開」の矛盾と、文言の実効性

- 再開には「どこまで処理したか」と「取得済み結果」の永続化が必要。(a) 進捗インデックスのみ永続化し失敗分はAPI再送（コスト増）、(b) 中間結果も永続化（個人情報がディスクに残る＝B1と連動）のどちらかを選ぶ意思決定が必要
- 「メモリ内のみで処理して破棄」は現行表現のままでは技術的に担保できない。GC言語のメモリ解放タイミングは制御不能で、OSのページファイル・ハイバネーション・クラッシュダンプへの書き出しはアプリから制御できない。要件文言は「アプリが管理する永続ストレージへ生JSONを書き出さない＋端末側のディスク暗号化で担保する」という二層の宣言に書き換えること
- この表現のまま顧客に「メモリ上でのみ処理し、残りません」と説明すると事実と異なる説明になる

### B5. 帳票の法定帳簿該当性

「来店年月日・金額・品目」＋本人確認情報の組み合わせは、業種によっては古物営業法の古物台帳や犯罪収益移転防止法の取引時確認記録に類似する構造を持つ（※構造の類似性の指摘であり該当の断定ではない）。該当する場合、記載事項の欠落許容度・保存期間・精度要件が法令側から降りてくる。業種と帳票の法的位置づけの確認が先。

## 4. 仕様確定が必要な指摘（設計着手前に決める）

### 4.1 出力仕様

- **CSVの1行が何を表すか**: 裏面明細（来店年月日/金額/品目）が複数件ある場合、1帳票1行（横展開・最大件数固定）か、1明細1行（表面情報を繰り返す）か。列定義はこれが決まるまで書けない
- **表裏の紐付けルール**: ファイル名規則か、スキャン順か。片面のみの帳票の有無。入力側で「この4枚が1セット」と保証されるか、ツール側が判別するのか（後者は難易度が跳ね上がる）
- **丸印判定の出力先**: 抽出項目リストに選択肢系カラムが存在しない。どの項目の選択肢か、CSVのどの列に何の値で出力するか。複数選択・無選択・「判定不能」の3値目の扱い
- **データ正規化ルール**: 生年月日（和暦/西暦、「S45.3.2」等の略記）、電話番号（先頭ゼロ保持。Excelの数値化対策で文字列指定必須）、金額（カンマ・円記号）、ふりがな（ひらがな/カタカナ統一）、備考欄の改行・カンマのクォート処理、CSVの文字コード（Excel直開き運用なら BOM付きUTF-8 が無難）、Excel形式（.xlsx、セル書式）
- **信頼度カラム**: 何の信頼度か（Vision APIのconfidenceか自前スコアか。丸印判定にはAPIのconfidenceが存在しないため自前定義が必要）。「納品時削除」は手作業だと誤納品事故の温床——作業用/納品用の2ファイル出力方式を推奨
- **ファイル名**: 命名規則、同名ファイル存在時の挙動（上書き/連番/エラー）

### 4.2 入力仕様

- **画像の取得経路と品質**: スキャナ（ADF）かスマホ撮影か。最低dpi、カラーモード（白黒二値で来ると手書きインク分離が困難）、形式（JPEG/PNG/TIFF/PDF）、傾き・影・台形歪みの許容範囲とリジェクト基準。スマホ撮影許容の有無だけで画像処理の規模が数倍変わる
- **記入方式**: 項目ごとに手書き/活字/ゴム印の別を表で確定。Vision の活字と手書きの精度は桁違い
- **様式のバージョン管理**: 改訂時の旧テンプレート保持、様式バージョンの自動判別かユーザー選択か
- **PDF入力の要否**: Cloud Vision の PDF 処理は非同期API＋クラウドストレージ経由が必要な場合がある ※要確認。その場合「ローカル完結」が崩れるため、画像のみで足りるなら PDF を外す判断もある

### 4.3 業務フロー

- **目検・修正工程**: ツール内（画像と抽出値を並べる確認UI）か、外（出力Excelを直接修正）か。**どちらもやらない選択肢はない**。ここが開発規模最大の分岐点（工数が数倍変わる）
- **納品経路**: 受け渡し手段の指定（禁止手段も明記。PPAP は対策として書かない）、誤送信対策、納品側控えの保持期間、納品前チェック手順（信頼度カラム削除の確認等）の手順化

### 4.4 セキュリティ・運用

- **データ資産一覧の作成**: ローカルに残るデータを全列挙し（元画像／位置合わせ後の中間画像／作業用CSV／納品用CSV/Excel／再開用中間データ／ログ／クラッシュダンプ／config／ライブラリの一時ファイル）、それぞれに保存場所・保持期間・保護・削除手段を定義する。列挙されていないデータは保護も削除もされない
- **認証情報の保管**: config に APIキー/サービスアカウントJSONを平文で置かない（最低ラインは Windows DPAPI）。IAM権限の最小化、クォータ・予算アラート設定（鍵漏洩時の被害上限）、ローテーション/失効手順
- **実行端末の前提**: ディスク暗号化必須（8GB低スペックPCは Windows Home の可能性あり→BitLocker可否の実機確認 ※要確認）、共有PC/共有アカウントの可否、出力先フォルダのACL、**OneDrive等の同期対象外パスの使用**、持ち出し可否
- **ログ設計**: 抽出値・氏名入りファイル名をログに書かない。出してよいID体系（ファイルID・ページ番号・ステップ名・エラーコード）を先に定義。例外メッセージに変数値を含めない規約。監査ログ（誰がいつ何件処理しどこへ出力したか）は事故時の影響範囲特定の唯一の材料。ログの保持期間・ローテーション
- **開発・テストデータ**: 実帳票を開発に使わない（ダミーデータ原則、実データ検証は指定端末・終了後削除）
- **失敗レコードの退避**: OCR失敗分を調査用に退避する場合、それもデータ資産一覧に載せる（削除漏れの定番箇所）
- **配布・更新**: 台数、インストーラ形態、管理者権限の可否、更新の配り方

### 4.5 技術前提

- **「4画像1送信」の目的の明確化**: Vision API は各画像を独立処理するため、得られるのはHTTP往復削減のみ。課金は画像×機能単位でまとめても安くならない ※要確認。表裏の紐付けにも寄与しない。部分失敗時のリトライ単位（1枚か4枚か）を再開要件とセットで定義
- **Vision の機能種別選定**: TEXT_DETECTION と DOCUMENT_TEXT_DETECTION は挙動・返却構造が異なり、座標マッピング設計が変わる
- **丸印判定（テンプレート減算方式）の成立条件**: 印字マスクの作成方法（原本スキャンか印刷データか）／スキャン条件の一様性（スマホ撮影許容と両立しない）／閾値チューニング用の正解ラベル付きサンプル（選択肢ごとに最低数十枚規模 ※経験則）／丸が閉じていない・二重丸・チェック・訂正等のバリエーションの扱い
- **JPEG圧縮と減算方式の競合**: Vision の画像サイズ上限 ※要確認 に合わせて再圧縮すると、圧縮ノイズが「残ったインク」と区別できなくなる。OCR送信用（縮小・圧縮）と丸印判定用（無加工原画像）を別系統にする許容の判断
- **メモリ予算の数値化**: 「8GB対応」ではなく「プロセスピーク使用量 N MB以下」の数値目標に。300dpi A4カラーは非圧縮で1枚25MB前後 ※概算、減算方式は中間バッファが複数並ぶ
- **API障害時挙動**: レート制限時のリトライ戦略（指数バックオフ・最大回数）、1実行あたりの送信枚数上限（設定ミスによる課金暴走の歯止め）
- **OSSライセンス確認フロー**: OpenCV・Excel生成ライブラリ等の候補が出た時点でライセンス確認レポートを起票する工程を要件に1行入れる（EPPlus のように商用条件が変わった経緯のあるライブラリもある ※要確認）

### 4.6 技術スタック（現時点では決めない・決めるための材料）

TypeScript/Python/Rust/Tauri/React は「言語・デスクトップシェル・UIフレームワーク」が混ざった並列で、このままでは比較できない。以下が要件で決まれば自ずと絞れる:

| 判断材料 | 効き方 |
|---|---|
| 配布形態（インストーラ/単一exe）・管理者権限の可否 | 単一exe必須なら Python は不利（肥大・起動遅延） |
| 対象OS | Windows のみか |
| 画像処理の重さ（スマホ撮影許容・減算方式採用の有無） | 重いなら OpenCV バインディングの充実した Python が最有力、Rust も可。TS単体は苦しい |
| 保守の引き継ぎ先スキルセット | Rust は人材制約が強い |
| GUI要否（利用者1〜2名ならCLI＋設定ファイル案もある） | GUI不要なら Tauri/React が丸ごと落ちる |

参考見立て（決定ではない）: 画像処理が重い構成なら Python + OpenCV、画像処理が最小限（業務スキャナ固定・傾き補正のみ）で配布容易性最優先なら Tauri（Rustコア + Web UI）。

## 5. 前提の問い直し（批判役の指摘）

- **「予算の兼ね合いでLLM不使用」の実数根拠がない**: Vision API と マルチモーダルLLM の従量単価比較 ※要確認、および丸印判定パイプラインを自作する開発工数の人件費換算が行われていない疑い。API従量費だけ見て開発工数を落とすと比較が成立しない
- **LLM排除の真の理由の一本化**: 理由が「コスト」なのか「個人情報を外部AIに渡したくない」なのか。後者なら Cloud Vision も同じく外部送信であり懸念は解消されていない
- **デスクトップGUI前提の根拠**: 利用者数・頻度が不明のままGUIを既定にすると、フロント実装・配布・低スペック対応のコストが自動的に積み上がる。1〜2名の定型バッチなら CLI＋設定ファイルで大きく削れる可能性
- **手法先行のサイン**: 丸印判定の手法詳細は決まっているのに、精度目標・検証サンプル数が未定。サンプル入手後に手法ごと作り直すリスク
- **建設的示唆（推奨アクション）**: 技術選定確定前に、実データ10〜20枚のタイムボックス・スパイクを実施する。(a) Vision API と候補サービス（Document AI 等 ※要確認）の項目別精度・単価の実測比較、(b) 丸印判定の自作プロトタイプの精度検証。結果を1枚の比較表にしてから形態（GUI/CLI）とアルゴリズムを確定する

## 6. 質問リスト（統合・優先度順）

### 最優先（回答がないと設計に着手できない）

1. 帳票の現物サンプル（表・裏）を数種類提供できるか。様式は何種類あり、旧様式は混在するか。無記入の原本（または印刷データ）は入手できるか
2. 抽出した個人情報を Google Cloud Vision へ送信することは、委託元との契約・社内規程・本人への利用目的通知の面で問題ないか。再委託条項の有無。NGの場合の方針（ローカルOCR代替 / 中止）
3. 外部通信が禁止された環境（閉域網・オフライン）での動作要件はあるか
4. この帳票を使う業種は何か。古物営業法・犯罪収益移転防止法等の法定帳簿・取引記録に該当するか。該当する場合の保存期間・記載事項要件
5. CSVの1行は何を表すか（1帳票1行で明細横展開 / 1明細1行）。明細の最大件数。「氏名2/生年月日2」は誰の情報で、2人固定か可変か
6. 表面と裏面をどう対応付けるか（ファイル名規則 / スキャン順）。片面のみの帳票はあるか
7. 出力後に人が確認・修正する工程は、ツールの中か外か
8. どの項目が何%正しく取れたら合格か（項目別）。目標未達時にリリースするか
9. LLM不使用の理由は「コスト」か「外部送信回避」か。コストなら比較の実数はあるか

### 高（機能仕様の確定に必要）

10. 各項目は手書きか活字（印字・ゴム印）か。項目別の内訳と手書き比率
11. 「族柄」は「続柄」の誤記か
12. 丸印判定はどの項目の選択肢か。選択肢の種類数、出力する値、複数選択・無選択・判定不能の扱い
13. 再開のために進捗・中間結果をディスクへ永続化することを許容するか。しない場合、失敗分のAPI再送（コスト増）でよいか。再開単位（ファイル/帳票セット/項目）
14. PDF入力は必須か。画像（JPEG/PNG）のみで足りるか
15. テンプレート（座標定義）は誰が作るか。現場ユーザーがGUIで新様式を追加する必要があるか、設定ファイルを開発側が用意する運用で足りるか
16. 画像の取得機器（スキャナ/複合機/スマホ）、dpi、カラーモード、傾き・歪みの実態
17. 「4画像1送信」の目的は何か（往復削減か、別の意図か）
18. 同一帳票が重複投入される可能性はあるか。重複検知は必要か（必要なら一意キーとなる帳票番号はあるか）

### 中（規模・運用・環境の見積に必要）

19. 月間・繁忙期ピークの処理枚数。1回のバッチ枚数
20. 現在の作業者数・所要時間。ツール化でどの程度短縮できれば投資に見合うか
21. 利用者数・PC台数・OSエディション（BitLocker可否）・実機スペック。「8GB」は実機確認済みの制約か。共有PC・共有アカウントの有無
22. 元画像/PDFの保持目的（再処理用か証跡か）・保持期間・削除の担当者。社内の保持期間規程はあるか
23. 信頼度カラムは「作業用ファイル」として納品用と別出力する運用でよいか
24. 納品先は誰か（社内別部署/社外）。受け渡し手段は既に決まっているか
25. 予算上限・希望納期。APIランニングコストの想定上限。Google Cloud の既存契約・DPA締結状況。プロジェクトの所有者（課金・IAM管理主体）
26. 出力ファイルの命名規則。同名ファイル存在時の挙動（上書き/連番/エラー)
27. PoC等で既に実データを Cloud Vision に送信した実績はあるか（ある場合、B1の整理は「既に送ったものの扱い」から始まる）
